# RussianDocs OCR — веб-сервис (эталонный пример интеграции)

Асинхронный REST-сервис поверх библиотеки [`document_processing`](../document_processing):
принимает изображение документа, ставит в очередь, отдаёт JSON с распознанными
полями и координатами найденных областей. Плюс веб-интерфейс: лог обработки,
детальная страница с отрисовкой блоков поверх выпрямленного изображения,
системные страницы.

> **Зачем он существует.** Это не «обвязка вокруг библиотеки», а демонстрация
> того, **как правильно вызывать эту библиотеку из сервиса**. Библиотека не
> потокобезопасна, грузит 215 МБ моделей, печатает в stdout, а её результат
> живёт до следующего вызова — всё это ловушки, на которые наступают при первой
> интеграции. Слой [`service/ml/`](ml/) написан так, чтобы показать каждую из
> них и способ обойти. Если вы читаете код в одном месте — читайте
> [`service/ml/runtime.py`](ml/runtime.py): его докстринг перечисляет
> **10 правил корректности** со ссылками на строки библиотеки.

**Библиотека при этом не модифицируется.** Сервис — обёртка; всё, что нужно
знать интегратору, выражено в его собственном коде.

## Быстрый старт

### Локально (основной режим разработки)

Нужно окружение с установленными `requirements2026.txt` + `requirements-service.txt`.
На машине разработки это conda-окружение `russiandocs`.

```bash
# бэкенд (порт 8002)
DATA_DIR=./data JWT_SECRET=dev-secret DEFAULT_API_KEY=rdk_local_dev \
  python -m uvicorn service.main:app --host 127.0.0.1 --port 8002
```

Фронтенд собирается один раз и раздаётся самим FastAPI:

```bash
cd web && npm run build
```

Для работы над интерфейсом удобнее dev-сервер с HMR (`cd web && npm run dev`,
порт 8000, проксирует `/api` на 8002).

Открыть <http://127.0.0.1:8002>, войти по PIN `1234`.

### В докере

```bash
docker build -t russiandocs:latest --build-arg GIT_COMMIT="$(git rev-parse --short HEAD)" .

# CPU
docker run -d --name rd-cpu -p 8003:8002 \
  -e COMPUTE_DEVICE=cpu -e JWT_SECRET=... -e DEFAULT_API_KEY=... russiandocs:latest

# GPU (нужен nvidia-container-runtime; на Windows — Docker Desktop с WSL2)
docker run -d --name rd-gpu --gpus all -p 8004:8002 \
  -e JWT_SECRET=... -e DEFAULT_API_KEY=... russiandocs:latest
```

**Контейнер работает от непривилегированного пользователя** `rdocs` (UID 10001). Это важно, если вы
монтируете свой каталог в `/app/data`: владелец на хосте останется хостовым, и первая же загрузка
упадёт с ошибкой прав — что читается как поломка сервиса, а не как проблема монтирования. Два способа:

```bash
# либо отдать каталог этому UID на хосте
sudo chown -R 10001:10001 /var/lib/rdocs-data
docker run -d -p 8002:8002 -v /var/lib/rdocs-data:/app/data russiandocs:latest

# либо запустить от своего пользователя
docker run -d -p 8002:8002 --user "$(id -u):$(id -g)"   -v /var/lib/rdocs-data:/app/data russiandocs:latest
```

Без монтирования (по умолчанию) ничего делать не нужно: каталог создан внутри образа и уже принадлежит
`rdocs`. Зачем это вообще — в [`SECURITY.md`](../SECURITY.md) §7: сервис скармливает **чужие файлы**
декодеру изображений и ONNX Runtime, и это ровно то место, где ошибка превращается в выполнение кода;
root там — разница между «шелл от rdocs» и «шелл, из которого начинают искать выход из контейнера».

**Образ один и тот же для GPU и CPU.** Отдельной CPU-сборки нет: в образе стоит
`onnxruntime-gpu`, он импортируется и без видеокарты, а сервис сам определяет,
что реально доступно, и пишет это в лог. Замеренные числа (RTX 4070 Ti SUPER,
паспорт 228 КБ): CPU — load 1434 мс, warmup 583 мс, документ 528 мс;
GPU — load 2135 мс, warmup 296 мс, документ 497 мс. Размер образа 7.72 ГБ
(из них база CUDA 868 МБ, pip 1.14 ГБ, модели 231 МБ).

`--workers 1` **обязателен** и не является настройкой производительности:
индекс хранилища и пайплайн живут в памяти процесса. `main.py` откажется
стартовать с другим значением.

## Аутентификация

Две схемы, потому что два разных типа вызывающего:

| | Чем | Что защищает |
|---|---|---|
| **Сайт** | PIN → JWT (HS256, 8 ч), `Authorization: Bearer` | вход в веб-интерфейс |
| **Эндпоинты** | `X-API-Key` | машинные вызовы |

Четырёхзначный PIN — это удобство для человека и плохой сервисный секрет: он
общий, угадываемый, и его пришлось бы вшивать в каждую интеграцию. API-ключ —
наоборот. Смешать их означало бы загнать один из двух сценариев в неподходящую
форму.

Рабочие эндпоинты (`/documents/*`) принимают **либо** ключ, **либо** сессию —
поэтому браузер и интеграция ходят одним и тем же путём, без дублирования
маршрутов. Управление ключами, настройки и логи — только сессия.

**Про дефолтный ключ.** Он всегда существует и не удаляется: иначе рестарт
(который стирает созданные в рантайме ключи) оставил бы API вовсе без доступа.
Значение берётся из `DEFAULT_API_KEY`; если переменная не задана — генерируется
случайный и печатается в лог при старте. Захардкоженного значения нет намеренно:
оно означало бы, что все забывшие настроить деплои делят один публично
известный ключ.

Хранится только `sha256`-хеш; полное значение показывается **один раз** при
создании; сравнение через `secrets.compare_digest`.

Картинки браузер тянет blob-фетчем с Bearer — `<img src>` не умеет заголовки, а
`?token=` в query сознательно не сделан: он утекает в логи и историю.

## REST API

Всё под `/api/v1`. `S` — сессия, `A|S` — ключ или сессия.

| Метод | Путь | Auth | Назначение |
|---|---|---|---|
| POST | `/auth/pin-login` | — | `{pin}` → `{access_token, user}` |
| POST | `/documents` | A\|S | multipart, один файл → **202** и строка списка |
| GET | `/documents` | A\|S | список: `status, doc_type, search, date_from/to, page, page_size, sort_by, sort_dir` |
| GET | `/documents/{id}` | A\|S | детальный JSON (контракт ниже) |
| GET | `/documents/{id}/progress` | A\|S | шаг, ETA, позиция в очереди |
| GET | `/documents/{id}/image/{canvas\|original\|thumb}` | A\|S | байты изображения |
| POST | `/documents/{id}/reprocess` | A\|S | переставить в очередь |
| DELETE | `/documents/{id}` | A\|S | 204 |
| POST | `/documents/purge` | S | очистить хранилище |
| GET/POST/DELETE | `/api-keys`, `/api-keys/{id}` | S | ключи |
| GET/PUT | `/settings` | S | schema-driven настройки |
| GET | `/status` | S | железо, рантайм, очередь |
| GET | `/logs` | S | кольцевой буфер |
| GET | `/health` | — | без префикса, для healthcheck |

### Контракт детального ответа

```json
{
  "doc_type": "INTPASSPORT_2011", "doc_conf": 0.99, "recognised": true,
  "canvas": {"url": "…/image/canvas", "width": 862, "height": 1255},
  "original": {"url": "…/image/original", "width": 897, "height": 1280},
  "coord_space": "canvas",
  "boxes": [{"id": "b6", "label": "Last_name_ru", "display": "Last name",
             "kind": "text", "x1": 402, "y1": 688, "x2": 905, "y2": 736,
             "conf": 0.92, "text": "ВАЛУЕВ"}],
  "fields": [{"name": "Last_name_ru", "display": "Last name", "value": "ВАЛУЕВ",
              "script": "ru", "conf": 0.92, "box_ids": ["b6"]}],
  "quality": {"Glare": "good", "Blur": "good",
              "PrintSpoofing": "REAL", "LCDSpoofing": "REAL"},
  "timings": {"total": 0.497, "_ocr": 0.174}
}
```

Три решения в этом контракте, каждое из-за конкретной проблемы:

- **`fields` — упорядоченный массив, а не словарь.** У словаря нет порядка
  чтения документа, а связь поля с боксом по равенству label ненадёжна:
  `Licence_number` на внутреннем паспорте детектится дважды (пайплайн
  дедуплицирует *поле*, не боксы), а составные поля вроде `Birth_place_ru` дают
  несколько боксов. Явные `box_ids` снимают это.
- **`coord_space: "canvas"`.** Боксы существуют **только** в системе координат
  выпрямленного изображения. Библиотека не сохраняет угол deskew, поэтому
  наложить их на исходную загруженную фотографию принципиально невозможно —
  интерфейс на виде «Original» оверлей не рисует и говорит почему, вместо того
  чтобы врать на величину перспективного преобразования.
- **`script` у поля** (`ru`/`en`/`num`) — фронтенд по нему выбирает шрифт.
  Моноширинный нужен для колонок цифр и уродует заглавную кириллицу (`Ш`, `Щ`,
  `Ж`, `Ы`), поэтому моно только для номеров, дат и кодов.

`progress` отдаёт `200` с телом `null`, когда сообщать нечего, а не `404`:
опрашивающий клиент иначе показывал бы ошибку каждые две секунды.

### Пример: загрузить и получить результат

```bash
curl -H "X-API-Key: $KEY" -F file=@samples/DL_2011/1_CR_DL_2010.jpg \
     http://127.0.0.1:8002/api/v1/documents          # -> 202 {"id": 8, ...}
curl -H "X-API-Key: $KEY" http://127.0.0.1:8002/api/v1/documents/8
```

Если сервис на localhost не отвечает, а вместо ответа приходит HTML —
скорее всего запрос ушёл через корпоративный прокси. Лечится `curl --noproxy '*'`.

## Прогон одного документа

[`service/example_client.py`](example_client.py) — готовый CLI на одной
стандартной библиотеке (копируется в любое окружение без установки):

```bash
RD_API_KEY=<ключ> python service/example_client.py path/to/document.jpg
```

Печатает тип документа, уверенность, устройство и время, качество, таблицу полей
со значениями и `box_ids`, число боксов, самые медленные стадии и ссылку на
страницу в веб-интерфейсе. Флаги: `--url`, `--key`, `--json`, `--save-canvas DIR`.

## Хранилище

Два бэкенда за одним протоколом [`core/store.py`](core/store.py):

| Режим | Когда | Поведение |
|---|---|---|
| **Временный** (по умолчанию) | `RUSSIANDOCS_DATABASE_CONNECTIONSTRING` не задана | JSON-файлы на диске, каталог **стирается при каждом старте** |
| **SQL** | переменная задана | MS SQL или PostgreSQL, миграции накатываются автоматически |

> **SQL здесь — справочная реализация, а не законченная функция.** Есть протокол
> хранилища с двумя реализациями, модели, миграция Alembic и 45 тестов,
> параметризованных по обоим бэкендам (на SQLite как подставке) — этого
> достаточно, чтобы доказать отсутствие диалектных допущений в самом сервисе и
> чтобы вы могли довести интеграцию под свою базу. Прогонов на живом MS SQL и
> PostgreSQL не было. По умолчанию база не используется вовсе.

> ### ⚠️ Включая SQL, вы включаете постоянное хранение персональных данных
>
> До этого момента хранилище **эфемерное**: каталог стирается при каждом старте, и это ограничивает
> ущерб само по себе. Как только вы задали строку подключения, распознанные паспорта начинают
> **храниться постоянно** — а в базе окажутся ФИО, дата и место рождения, серия и номер документа,
> адрес регистрации, и рядом на файловой системе останутся сами изображения с фотографией лица.
>
> **Просто так хранить это нельзя.** Фотография лица, используемая для установления личности, — это
> биометрические персональные данные (ст. 11 152-ФЗ), для которых по общему правилу требуется
> **письменное согласие** субъекта. Кроме согласия закон потребует правового основания, уведомления
> Роскомнадзора, локализации базы **на территории РФ** (ст. 18 ч. 5), установленного срока хранения с
> уничтожением по его истечении, определения уровня защищённости и мер по приказу ФСТЭК № 21.
>
> **Оператором персональных данных становитесь вы, а не авторы библиотеки.** Прежде чем включать SQL в
> production, прочитайте [`SECURITY.md`](../SECURITY.md) — там по фактам кода перечислено, что именно
> и где сохраняется, чек-лист по 152-ФЗ и то, чего этот софт **не** делает (нет шифрования на диске,
> нет автоудаления по сроку, нет аудита действий). Реквизиты и ссылки на нормативные акты —
> в [`docs/legal-links.md`](../docs/legal-links.md).
>
> Практический минимум, если решение принято: шифрованный том под базу и под каталог артефактов,
> ретенция (её в софте нет — реализуете сами), TLS до базы, отдельная учётная запись СУБД с
> минимальными правами, и резервные копии на тех же условиях, что и сама база — они тоже персональные
> данные.

```bash
RUSSIANDOCS_DATABASE_CONNECTIONSTRING=postgresql+psycopg://user:pass@host:5432/russiandocs
RUSSIANDOCS_DATABASE_CONNECTIONSTRING="mssql+pyodbc://user:pass@host:1433/russiandocs?driver=ODBC+Driver+18+for+SQL+Server&TrustServerCertificate=yes"
```

Без переменной сервис печатает при старте рамку-предупреждение, что данные
теряются. Это громко намеренно: молчаливая потеря данных — худший вариант.

**Сервис никогда не деградирует молча.** Если строка задана, но база
недостижима — он падает, а не откатывается на временное хранилище: откат
выглядел бы как «всё работает» и тихо выбрасывал данные, ради которых базу и
настраивали.

Бинарные артефакты (оригинал, canvas, миниатюра) остаются на файловой системе в
**обоих** режимах — многомегабайтные PNG не место в строке таблицы. В реальном
деплое этот слой заменяется на S3, а не на BLOB-колонку, поэтому он и вынесен в
отдельный [`repositories/artifacts.py`](repositories/artifacts.py).

Для MS SQL в докер-образ нужно добавить `msodbcsql18` — сейчас он не ставится
(≈100 МБ и EULA в каждой сборке), стоит только `unixodbc`, которого хватает,
чтобы `pyodbc` импортировался.

## Сид-документы

Пустой лог — плохое первое впечатление и бесполезное: кликать нечего, ничто не
показывает, что сервис делает. Поэтому в пустое хранилище добавляются 7
документов — по одному на каждый поддерживаемый тип.

**Результаты предпосчитаны и лежат в репозитории** ([`seed_data/`](seed_data),
1.0 МБ): `result.json` + `canvas.jpg` + `thumb.jpg` на документ. Сид — это
копирование файлов: ни GPU, ни загрузки моделей, ни задержки старта, и одни и те
же строки на любом железе. Последнее свойство делает их ещё и golden-файлами для
порта на другой язык.

Перегенерировать после изменений в библиотеке (иначе строки описывают поведение
старой версии):

```bash
python service/tools/build_seed_data.py
```

Оригиналы в фикстурах не дублируются — они уже лежат в `samples/`, манифест
хранит путь. Canvas в JPEG, а не PNG: это подложка под SVG-оверлеем, а PNG
раздувал набор впятеро.

## Как это устроено

```
POST /documents ──> валидация ──> байты на диск ──> строка в очередь ──> 202
                                                          │
                     drain-loop (asyncio) <───────── _WAKE.set()
                                │
                  ThreadPoolExecutor (CPU-работа вне event-loop)
                                │
                  lease_pipeline() ─── Pipeline.process_img ─── build_viewmodel
                                │            (всё внутри лизы!)
                     canvas/thumb на диск + результат в хранилище
```

| Файл | Ответственность |
|---|---|
| [`ml/runtime.py`](ml/runtime.py) | **ядро примера**: жизненный цикл, выбор устройства, лиза пайплайна, прогрев, диагностика окружения |
| [`ml/transform.py`](ml/transform.py) | `PipelineResults` → JSON-safe viewmodel, все касты numpy |
| [`ml/labels.py`](ml/labels.py) | человеческие названия полей, порядок, определение письменности |
| [`worker.py`](worker.py) | drain-loop, дисциплина лизы, таймауты, ретраи, прогресс |
| [`core/database.py`](core/database.py) | файловое хранилище: индекс в памяти, атомарная запись |
| [`core/db_sql.py`](core/db_sql.py) | тот же протокол на SQLAlchemy 2.0 |
| [`repositories/`](repositories) | запросы и денормализация; подписи функций — контракт миграции на SQL |
| [`api/`](api) | роутеры; сериализация руками, чтобы формат был виден в одном месте |
| [`../web/`](../web) | Vue 3.5 + TS SPA; оверлей боксов — SVG с `viewBox` в пикселях canvas |

## Страница-демонстрация интеграции и TypeScript-клиент

В сайдбаре под **Documents** есть страница **Integration demo** (`/integration`). Она не ещё один
экран загрузки: это рабочий пример того, как **сторонний сайт** обращается к сервису, и на самой
странице это написано первым абзацем.

Что на ней происходит:

1. **Сервис определяется сам.** Переключателя портов нет: страница опрашивает `GET /health` по
   известным адресам — свой origin, затем `8002` (Python), `8003` (Go), `8004` (.NET), `8005`
   (Kotlin/JVM) — и берёт первый ответивший, предпочитая тот, который её же и отдал. Порт, который
   отвечает `no response`, либо не запущен, либо не перечислил этот origin в
   `CORS_ALLOWED_ORIGINS`; браузер сознательно не говорит, что именно, поэтому и страница не говорит.
2. **Документ уходит через тот же REST**, что и любая интеграция: `POST /documents` → опрос →
   `GET /documents/{id}/image/canvas`. Каждый вызов показан с методом, путём, кодом и временем, а
   рядом — та строка TypeScript, которая его сделала.
3. **Результат отрисован как на странице документа**: канвас с наложенными боксами, таблица полей со
   связью «поле ↔ бокс» по наведению, качество, тайминги, raw JSON.

Клиент — **один файл без зависимостей**: [`web/src/client/rdocs-client.ts`](../web/src/client/rdocs-client.ts).
Только `fetch`/`FormData`/`URL`, поэтому копируется в любой сайт (Vue, React, Svelte, чистый HTML) и в
Node 18+ без изменений. Он работает со всеми четырьмя реализациями — контракт один, различаются только
порты.

```ts
import { createClient } from './rdocs-client'

const rdocs = createClient({ baseUrl: 'http://localhost:8002', apiKey: 'rdk_…' })
const { result } = await rdocs.recognise(file)
console.log(result.doc_type, result.ocr)
```

Пять вещей, которые клиент документирует и в которые легко влететь (полный текст — в шапке файла):
распознавание **асинхронное** (`202`, потом опрос); `/progress` отвечает `200` с JSON `null`, а не
`404`; картинки нужно **забирать fetch'ем**, потому что `<img src>` не умеет отправить заголовок, а
токен в query-строке утёк бы в логи; координаты боксов — **в пространстве канваса** и на исходное фото
не переносятся; и **CORS** — чужой origin должен быть в `CORS_ALLOWED_ORIGINS` целевого сервиса.

## Правила интеграции (главное)

Полный список с номерами и ссылками на строки библиотеки — в докстринге
[`ml/runtime.py`](ml/runtime.py). Здесь то, без чего интеграция ломается
незаметно:

1. **`Pipeline` не потокобезопасен.** `process_img` переприсваивает
   `self.results` и `self.ocr_options`. Два одновременных вызова молча вернут
   результаты друг друга — худший класс бага для документов, и он не
   воспроизводится при ручной проверке в одиночку. Отсюда `lease_pipeline()`:
   **никогда** не звать `process_img` вне лизы.
2. **Преобразовывать результат нужно ВНУТРИ лизы.** `results` — это и есть
   `pipeline.results`; следующий `process_img` его переприсвоит. Чтение после
   освобождения лизы — гонка, а не теория.
3. **`Pipeline.warmup()` использовать нельзя**: он ловит всё в голый `except` и
   печатает — не может ни бросить, ни попасть в структурный лог. Звать
   `process_img` напрямую.
4. **Прогрев нужен реальным документом.** Без аргумента подставляется
   синтетический серый кадр, который классифицируется как `'NONE'` и коротит до
   OCR — прогреется только начало цепочки. Брать файл из `samples/` (и **только**
   обезличенный: прогрев читает файл при каждом старте).
5. **Библиотека печатает в stdout** — оборачивать `contextlib.redirect_stdout`,
   иначе её вывод перемешается со структурными логами. На пути ошибки этот текст
   единственное описание причины, поэтому там он повышается до WARNING.
6. **`'CUDAExecutionProvider' in get_available_providers()` не доказывает рабочий
   GPU** — провайдер числится просто потому, что установлен пакет. Единственная
   честная проверка — построить `Pipeline` и поймать исключение. Но и её
   недостаточно: **в контейнере без `--gpus` провайдер не бросает исключение, а
   роняет процесс сегфолтом**, поэтому есть ещё `gpu_visible()` (NVML +
   device-ноды), и CUDA не пробуется, если устройства не видно.
7. **При `device='gpu'` OCR всё равно на CPU** — так и задумано (динамическая
   ширина на CUDA-провайдере в сотни раз медленнее на вызов). Статус-страница
   показывает `device` и `ocr_device` раздельно, иначе первый же взгляд в
   `nvidia-smi` породит баг-репорт. Следствие: OCR чувствителен к посторонней
   нагрузке на процессор.
8. **215 МБ моделей грузятся жадно в `__init__`** — инстанс дорогой, второй на
   одной видеокарте это второй CUDA-контекст. Пул размера 1 — осознанное
   значение, а не заглушка.
9. **`ndarray` на входе должен быть RGB**, а `cv2.imwrite` ждёт BGR. Пропущенный
   `cvtColor` меняет местами красный и синий на каждом документе и выглядит
   достаточно правдоподобно, чтобы уехать в прод. На это есть тест.
10. **Только `ml/` импортирует `document_processing`.** Всё остальное общается с
    ним через узкий интерфейс — поэтому при переписывании на другой язык
    меняется внутренность одного модуля, а фронтенд и контракт не меняются вовсе.

Ещё две ловушки не в библиотеке, а в самом сервисе:

- **`asyncio.wait_for` не убивает поток исполнителя.** Зависший `process_img`
  продолжает держать лизу. Задача возвращается в очередь, статус становится
  `degraded`; полного решения внутри процесса нет, последняя линия обороны —
  `restart_policy`.
- **Байты на диск раньше, чем строка в очередь.** Обратный порядок оставляет
  окно, в котором drain-loop заберёт документ, чей файл ещё не записан, и
  хорошая загрузка станет `failed`.

## Грабли, на которые мы уже наступили

Найдено на практике, не в теории:

- **Windows-разделители в путях библиотеки.** `joinpath(r'dictionary\fms_unit.csv')`
  и `working_dir / 'resources\centers.npz'` на POSIX — это одно имя файла, а не
  путь. Библиотека **не импортировалась в Linux-контейнере** вообще; на Windows
  работало годами. Нормализация вынесена в код, артефакты не переделывались.
- **`npm ci` в контейнере падает с `E401` Nexus** — lock-файл резолвит тарболы
  через корпоративное зеркало, а учётных данных внутри нет. В стадии сборки хост
  переписывается на публичный реестр; `integrity`-хеши те же и проверяются.
- **`.dockerignore` из соседних проектов начинается с `*.json`** — скопировав
  как есть, вы молча выкинете `models/*/ONNX/model.json` (формы входов, списки
  классов, шаги пре/постобработки). Образ соберётся и умрёт на первом
  `Pipeline()`. Здесь ignore написан как allowlist, плюс сборка проверяет
  количество моделей.
- **`docker restart` сохраняет writable-слой.** Отсутствия тома недостаточно,
  чтобы данные исчезали — отсюда `DATA_WIPE_ON_START=true`.
- **Файлы из `public/` Vite не хэширует** — единственный файл, который браузер
  мог отдать устаревшим после деплоя, это дизайн-система. Ссылка на неё
  штампуется версией сборки.
- **Кэш картинок против Reprocess.** `max-age` на `/image/{kind}` означает, что
  после повторной обработки браузер показывает прежнюю картинку рядом с уже
  новой таблицей полей. Нужен `no-cache` (это «перепроверь», а не «не храни»:
  повторный запрос стоит 304 без тела).
- **Приоритет настроек.** Переменные окружения и хранилище настроек должны
  **накладываться** (хранилище → env → схема), а не конкурировать. Иначе
  `COMPUTE_DEVICE=cpu` пишется в лог и игнорируется, а страница настроек
  показывает не то устройство, на котором сервис работает.
