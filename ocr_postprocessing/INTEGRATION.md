встроена, достаточно заменить `model.onnx`: код не меняется.

| | |
|---|---|
| вход | `image`: `uint8 [1, 32, W, 3]`, **BGR**, высота 32, ширина любая (до 1024); нормализация внутри графа |
| выход | `probs`: `float32 [1, T, C]` — softmax по кадрам; столбец 0 — blank, столбец `i > 0` — `Alphabet[i-1]` |
| алфавит | 53 символа: `` "(),-./:№0123456789АБВГДЕЁЖЗИЙКЛМНОПРСТУФХЦЧШЩЪЫЬЭЮЯ`` (первый — пробел) |
| рантайм | onnxruntime, CPU (так быстрее и точнее, чем CUDA, для переменной ширины) |

**Подготовка лоскута — ровно как при обучении**, иначе точность падает:

```python
import cv2, numpy as np, onnxruntime as ort
from PIL import Image

sess = ort.InferenceSession('onnx/model.onnx', providers=['CPUExecutionProvider'])
inp = sess.get_inputs()[0].name

def ocr_probs(crop_bgr: np.ndarray) -> np.ndarray:
    """Лоскут BGR uint8 любого размера -> матрица [T, C]."""
    h, w = crop_bgr.shape[:2]
    rgb = cv2.cvtColor(crop_bgr, cv2.COLOR_BGR2RGB)
    img = Image.fromarray(rgb).resize((min(1024, max(1, int(w * 32 / max(1, h)))), 32), Image.BILINEAR)
    x = np.asarray(img, dtype=np.uint8)[..., ::-1][None].copy()      # обратно в BGR, [1, 32, W, 3]
    return sess.run(None, {inp: x})[0][0]
```

Масштабирование — PIL bilinear до высоты 32 с сохранением пропорций. Не cv2.resize и не
растягивание до фиксированной ширины.

**Проверка после встраивания.** Прогони свои лоскуты замороженного теста:
- полная строка верна примерно в 87 % (сравнение без пробелов и точек, Ё = Е);
- у v3 на том же тесте было 62,5 %.

Если вышло заметно ниже — почти наверняка не та подготовка лоскута.

**Точность T031**, полная строка: новый тест (1 235 лоскутов) — 87,0 %; эталон 515 штампов

## 2. Улучшатель `ocr_postprocessing`

Пакет лежит в корне репозитория: `ocr_postprocessing/`. Он не зависит ни от сервиса, ни от
`document_processing`. Зависимости:
- `numpy`, `rapidfuzz` (3.14.6);
- `opencv-python` — только для входа рамок сервиса.

**Как перенести к себе.** Скопируй папку `ocr_postprocessing/` целиком и три справочника из
`service/ml/registration/assets/`:

| файл | что это |
|---|---|
| `addressru.zip` | КЛАДР/ФИАС |
| `fms_unit_2026-09-22.csv` | коды подразделений |
| `street_names_kladr.json` | частые названия улиц |

Пути к справочникам задай одним из двух способов:
- явно: `References(addressru=..., fms_csv=..., street_names=...)`;
- переменными окружения `RDOCS_ADDRESSRU`, `RDOCS_FMS_UNIT`, `RDOCS_STREET_NAMES`.

**Что надо знать об объекте `OCRPostprocessor`:**
- создавай его один раз на процесс: справочники загружаются в память, ~2,5 с, после первого запуска;
- индекс пунктов строится один раз (~5 с) и кэшируется в `~/.cache/ocr_postprocessing/` (или в
  `RDOCS_REFS_CACHE`);
- объект не потокобезопасен: кэши — обычные словари. На каждый поток — свой объект или блокировка.

### Вариант А — лоскут без штампа

Подходит, когда соседних полей нет: тест лоскутов, поток без группировки по штампу.

```python
from ocr_postprocessing.crop import CropImprover
imp = CropImprover('путь/к/onnx')                  # папка модели: алфавит берётся из model.json
r = imp.improve(label, ocr_probs(crop))
r['text']      # улучшенное чтение — в том же виде, как пишется на штампе
r['raw']       # лучший путь CTC без улучшения
r['value']     # для даты 'ДД.ММ.ГГГГ', для номера '17А', для кода 'NNN-NNN' (если есть)
r['changed'], r['rule']
```

### Вариант Б — штамп целиком (лучше)

Если лоскуты сгруппированы по штампу, улучшатель использует связи полей. Код даёт регион и название
подразделения, найденный пункт даёт свои улицы, в строки попадают названия, найденные для этого штампа.

```python
from ocr_postprocessing import OCRPostprocessor
pp = OCRPostprocessor('путь/к/onnx')
res = pp.process_crops([{'label': lab, 'probs': ocr_probs(crop), 'id': crop_id} for lab, crop, crop_id in stamp])
for f in res['fields']:          # те же поля в том же порядке; 'probs' убран, свои ключи ('id') сохранены
    f['text'], f['raw'], f['changed']
res['stamp']    # {'date': '18.10.2007', 'region': ..., 'district': ..., 'locality': ..., 'street': ...,
                #  'house': ..., 'building': ..., 'flat': ..., 'code': '250-044'} — только найденное
```

Метки — классы твоей сети: `date, addr_line, issuer_line, code, house, flat, korp`. Порядок лоскутов
желательно передавать сверху вниз: так названия, перенесённые со строки на строку, склеиваются лучше.

### Что получится (OCR v4-T031, твои лоскуты, замороженный тест)

| | без улучшателя | вариант А (лоскут) | вариант Б (штамп) |
|---|---|---|---|
| тест (1 237) | 86,8 % | 90,4 % (исправлено 45, испорчено 1) | **90,8 %** (+50 / −1) |
| проверка (1 104) | 86,0 % | 89,9 % | **90,3 %** |

Больше всего растут строки:
- адреса: 83,1 → 90,1 %;
- «кем выдано»: 76,1 → 81,6 %.

Скорость на CPU:
- лоскут — меньше 1 мс (до ~0,1 с, когда дату приходится перебирать);
- штамп — медиана 30 мс, максимум ~0,35 с.

### Проверка, что всё встало


## 3. Ручки (менять только с замером)

| где | ручка | сейчас | что делает |
|---|---|---|---|
| `CropImprover` | `word_margin` | 10 | насколько матрица может «не любить» словарное слово; меньше — осторожнее (6: 89,7 %, 10: 90,4 %, 15: 90,5 % и больше порч) |
| `CropImprover` | `rules_on` | все четыре | отключить правило: `('date', 'number', 'code')` — без словаря слов |
| `OCRPostprocessor` | `place_margin` | 8 | то же для региона, района и пункта по матрице |
| `OCRPostprocessor` | `street_limit` | 150 | сколько похожих улиц пункта оценивать по матрице |

## 4. Чего улучшатель не делает

- **Не запускает OCR и не режет штамп.** Ему нужны готовые матрицы.
- **Не придумывает текст, которого сеть не видела.** Справочник подсказывает, решает матрица.
- **Не учитывает подписи, не похожие ни на одно поле** («ОБЩ.», «10, КОМ. 16» в квартире): они проходят как прочитаны.
