# RussianDocsOCR

Открытая библиотека для **распознавания и валидации документов граждan РФ** по одному
изображению (фото с телефона или скан) — без специального оборудования.

Проект: [github.com/protei300/RussianDocsOCR](https://github.com/protei300/RussianDocsOCR) ·
Лицензия [**MIT**](LICENSE) — она покрывает и код, и **обученные веса моделей** (215 МБ, качаются
[отдельным шагом](#установка) в `document_processing/models/`); подробности и сторонние
компоненты — в [`NOTICE`](NOTICE) ·
при поддержке Фонда содействия инновациям.

> Этот README — точка входа и для человека, и для ИИ-ассистента (Claude). Раздел
> [«Быстрая интеграция для Claude»](#быстрая-интеграция-для-claude) даёт пошаговый
> рецепт, чтобы подключить библиотеку в другой проект за пару минут.

> **Нужен готовый сервис, а не библиотека?** В репозитории есть эталонный
> асинхронный REST-сервис с веб-интерфейсом: очередь, JSON с полями и
> координатами найденных областей, отрисовка блоков поверх выпрямленного
> изображения, один docker-образ для GPU и CPU. Он написан в первую очередь как
> **демонстрация того, как правильно вызывать эту библиотеку из сервиса** —
> библиотека не потокобезопасна, грузит 215 МБ моделей и её результат живёт до
> следующего вызова, и все эти ловушки в нём разобраны по пунктам.
> Документация: [`service/README.md`](service/README.md).

> **Собираетесь обрабатывать настоящие документы?** Прочитайте
> [`SECURITY.md`](SECURITY.md) до развёртывания. Коротко: обработка полностью локальная, ничего не
> уходит наружу — но **оператором персональных данных становитесь вы**, а изображение паспорта
> содержит биометрию (фотографию лица), для которой закон требует отдельного основания. Там же по
> фактам кода перечислено, что и где сохраняется, чего софт **не** делает (нет TLS, нет шифрования на
> диске, нет автоудаления по сроку), и чек-лист безопасного развёртывания. Про сам проект там же сказано
> отдельно: **своих персональных данных у него нет** — точность измерялась внутри контура заказчика, а
> в репозитории лежат только обезличенные образцы ([`samples/README.md`](samples/README.md)).

> **Нужна не Python?** Библиотека и сервис существуют в **четырёх реализациях одного контракта** —
> Python, Go, .NET и Kotlin/JVM. Это не переводы «на глаз»: каждая сверяется с питоновским эталоном
> по 44 стадиям конвейера на семи документах, до последней цифры.
> Обзор и сравнение: [`ports/README.md`](ports/README.md).

| Реализация | Как подключить | Сервис на порту | Сходимость с эталоном |
|---|---|---|---|
| **Python** (эталон) | [«Быстрая интеграция»](#быстрая-интеграция-для-claude) | 8002 | задаёт golden-файлы |
| **Go** | [`ports/go/README.md`](ports/go/README.md) | 8003 | 44/44 стадии, CPU и GPU |
| **.NET 8** | [`ports/dotnet/README.md`](ports/dotnet/README.md) | 8004 | 44/44 стадии, CPU и GPU |
| **Kotlin/JVM** | [`ports/java/README.md`](ports/java/README.md) | 8005 | 44/44 стадии, CPU и GPU |

Все четыре сервиса отдают один и тот же REST и один и тот же веб-интерфейс (`web/`), поэтому клиенту
они неразличимы. Для браузера и Node есть готовый клиент без зависимостей —
[`web/src/client/rdocs-client.ts`](web/src/client/rdocs-client.ts), плюс страница `/integration`,
которая показывает интеграцию сайта с сервисом на живых вызовах.

Чего в портах **нет** намеренно: страница регистрации внутреннего паспорта (`INTPASSPORTADDR`)
реализована только в Python — для неё нет обезличенного образца, а значит нет и golden-файла, по
которому порт можно проверить. Это ограничение данных, а не кода.

## Точность

Измерено на **50 000 внутригражданских паспортов РФ** — снимки, которые люди делали сами, подавая заявку
на кредит: телефон, посторонний фон, блики, наклон. Прогон выполнялся **в ДМЗ заказчика**: сами документы
нам не передавались, наружу уходила только метрика — поэтому набор и невозможно опубликовать. Условия:
GPU, короткая сторона снимка больше 900 пикселей.

| | |
|---|---|
| Классификация типа документа | **99,01 %** |
| Детекция полей — точность / полнота | **98,4 % / 99,8 %** |
| Распознавание русского текста с фоном | **не ниже 97 %** по всем полям |

OCR против открытых движков на том же наборе (средняя метрика качества):

| Движок | Русский | Английский |
|---|---|---|
| **RussianDocs** | **0,9745** | **0,9721** |
| PaddleOCR | 0,92 | 0,96 |
| EasyOCR | 0,8044 | 0,9133 |
| Tesseract OCR | 0,4118 | 0,5051 |

Разрыв — на **русском**; на английском PaddleOCR подходит вплотную (0,96 против 0,9721), и на одном
закрытом наборе такая разница вполне может быть шумом.

Метрика — `1 − средний нормированный Левенштейн` по всем возвращаемым полям, с нормировкой на максимум
длин эталона и предсказания. **Это не CER** и с CER-числами из чужих README не сравнивается: формула,
причина и оговорки — в [`docs/accuracy.md`](docs/accuracy.md).

⚠️ **Цифры получены на legacy-генерации OCR — не на тех моделях, что шипятся сейчас.** Актуальные модели
v2 по внутренним замерам заметно лучше (средний CER 0,123 → 0,062), но **прогона v2 на этих 50 000
документах не было**, а повторить его можно только там же, в ДМЗ. То есть опубликованное — нижняя граница
на старых весах, а не «стало лучше на столько-то».

**Ещё две оговорки, без которых числа читаются шире, чем следует.** Выборка — паспорта одного типа, поэтому
99,01 % классификации это про «узнать паспорт», а не про матрицу ошибок между пятью типами документов. И
**худшее поле — место рождения**: свободный текст с сокращениями и переносами; именно оно определяет, сколько
документов придётся смотреть человеком, а среднее по полям его скрывает.

Это измерения производителя на закрытом наборе — он состоит из реальных документов и опубликован быть
не может, поэтому проверить их со стороны нельзя. Чего в этих числах пока **нет** (размер выборки,
версия моделей, разбивка по полям) — там же.
Проверить на своих данных: `python scripts/eval_quality.py`.

## Что умеет

Из одного изображения:
- определяет **тип документа** и угол (кратно 90°), разворачивает изображение;
- оценивает **качество** (блики, размытие, экранная/печатная подмена);
- находит границы документа, исправляет перспективу и остаточный наклон;
- локализует текстовые поля, режет на слова;
- распознаёт текст (**OCR**) — кириллица и латиница.

**Поддерживаемые типы:** водительские удостоверения (2011–2019, 2020+), общегражданские
паспорта (1997–2011, 2011+), СНИЛС (1996+), загранпаспорта (биометрия 2007+, без 2003+),
страница регистрации внутреннего паспорта (адрес).

## Требования

- **Python 3.10–3.12** (рекомендуется; библиотека также работает на 3.9+ со старым набором зависимостей — см. ниже).
- Зависимости — **[`requirements2026.txt`](requirements2026.txt) (рекомендуется, по умолчанию)**: современный проверенный набор (numpy 2.2, onnxruntime 1.21, opencv 4.12, scikit-learn 1.7, …). Валидирован end-to-end в чистом окружении: полный тест-сьют и `process_img` на CPU и GPU дают идентичный результат.
  Старый [`requirements.txt`](requirements.txt) оставлен для обратной совместимости (numpy 1.26, onnxruntime 1.16) — используйте только если новый набор конфликтует с другими зависимостями вашего проекта.
- Для **GPU**: вместо `onnxruntime` поставить `onnxruntime-gpu` (та же версия, что в requirements-файле) и иметь CUDA/cuDNN (для RTX 40xx — CUDA 12.x + cuDNN 9). Подробнее ниже в [GPU](#gpu).

## Установка

### Как pip-пакет (библиотека)

```bash
pip install git+https://github.com/protei300/RussianDocsOCR.git
rdocs-fetch-models   # веса (215 МБ) скачаются в установленный пакет и проверятся по SHA-256
```

Импорт — `from document_processing import Pipeline` (пакет верхнего уровня; обёртки
`russian_docs_ocr.` из версий 3.x больше нет). В дистрибутив входит только библиотека:
сервис, порты и conformance-харнесс живут в репозитории. Для GPU после установки:
`pip uninstall onnxruntime -y && pip install onnxruntime-gpu==1.21.1`.

### Из клона репозитория (разработка, сервис, тесты)

```bash
# 1. получить код (репозиторий лёгкий — весов в нём нет)
git clone https://github.com/protei300/RussianDocsOCR.git
cd RussianDocsOCR

# 2. скачать веса моделей (215 МБ) — ассеты релиза, проверяются по SHA-256
python scripts/fetch_models.py

# 3. зависимости (CPU) — рекомендуемый современный набор
pip install -r requirements2026.txt
#    для GPU: pip uninstall onnxruntime -y && pip install onnxruntime-gpu==1.21.1

# альтернатива: старый набор (numpy 1.26 / onnxruntime 1.16), для совместимости
# pip install -r requirements.txt
```

**Про веса.** Они не лежат в git — это 215 МБ бинарников, которые тянулись бы при каждом клоне и
навсегда оседали в истории. Вместо этого их состав зафиксирован в
[`document_processing/models.lock.json`](document_processing/models.lock.json) (путь, размер и
SHA-256 каждого из 29 файлов), а сами файлы лежат ассетами релиза — тег в манифесте и привязывает
набор к версии библиотеки. Лицензия та же MIT, что и у кода.

Загрузчик написан на стандартной библиотеке (работает до `pip install`), качает только
недостающее и несовпадающее, проверяет контрольные суммы и пишет файл атомарно — недокачанный вес
не превратится в загадочную ошибку распознавания.

```bash
python scripts/fetch_models.py --check   # проверить, что набор на месте и цел
python scripts/fetch_models.py --force   # перекачать всё
```

**Закрытый контур.** Зеркалируйте ассеты внутрь периметра и укажите
`RDOCS_MODELS_URL=https://зеркало.внутри/rdocs/models/` — код менять не нужно. Если веса уже
разложены где-то ещё, на них указывает `RDOCS_MODELS_ROOT` (та же переменная, что используют
порты на Go, .NET и Kotlin).

В своём проекте нужно, чтобы каталог `document_processing/` (вместе с `models/`) был
импортируем. Самый простой способ — добавить корень репозитория в `sys.path`:

```python
import sys
sys.path.insert(0, "/путь/к/RussianDocsOCR")
from document_processing import Pipeline
```

Либо скопировать каталог `document_processing/` (со всеми `models/`) внутрь своего проекта.

## Быстрый старт

```python
from document_processing import Pipeline

# device=None -> авто (GPU если есть CUDA, иначе CPU)
# ocr='accurate' (по умолчанию) | 'fast'
pipeline = Pipeline(device=None, ocr='accurate')

results = pipeline.process_img('path/to/passport.jpg')

```

Полный результат одним словарём:

```python
report = results.full_report   # {'DocType':..., 'OCR':..., 'Quality':..., 'Timings':...}
```

## API

### `Pipeline(model_format='ONNX', device=None, ocr='accurate', verbose=False, ocr_gpu_batch=False)`

| параметр | значения | описание |
|---|---|---|
| `model_format` | `'ONNX'` (реком.), `'OpenVINO'` | какой **движок** исполняет модели детекторов. Веса одни и те же (`.onnx`) — OpenVINO читает их напрямую, отдельного набора весов под формат больше нет. OCR всегда на onnxruntime |
| `device` | `None`, `'cpu'`, `'gpu'` | `None` → авто-выбор GPU→CPU по доступным провайдерам onnxruntime; см. ниже про OCR на GPU |
| `ocr` | `'accurate'`, `'fast'` | движок OCR (см. ниже) |
| `verbose` | `bool` | лог загрузки моделей |
| `ocr_gpu_batch` | `bool` (по умолч. `False`) | ЭКСПЕРИМЕНТАЛЬНО: батчинг OCR на GPU, см. ниже |

> **Прямые вызовы модулей.** У `Pipeline` движок задаётся через `model_format`, а у отдельных
> модулей это два независимых аргумента: `model_format` выбирает **папку артефакта**, `runtime` —
> **движок исполнения**. Под OpenVINO нужно передавать `runtime`, иначе загрузится onnxruntime:
> ```python
> Blur(model_format='ONNX', runtime='OpenVINO', device='cpu')
> ```
> Порядок выбора движка: аргумент `runtime` → ключ `"Runtime"` в `model.json` → расширение файла.

**Движки OCR:**
- `'accurate'` (по умолчанию) — новые модели MobileNetV4, максимальная точность;
- `'fast'` — новые модели EdgeNext, быстрее, чуть ниже точность.

> **Убрано в 3.0.0:** `ocr='legacy'` (исходные модели rus / eng+nums), флаг `fv_ocr` и путь
> CTC-regex. Легаси-движок делал заметно больше символьных подмен, а FV-путь проигрывал
> обычному greedy по CER — держали его только ради обратной совместимости. Передача
> `ocr='legacy'` теперь бросает `ValueError` с этим пояснением.

**Важно про GPU и OCR:** оба движка — модели с динамической шириной входа; при поштучной подаче (как это устроено в пайплайне) на CUDA-провайдере ONNX Runtime каждое слово новой ширины перекомпилирует граф — на GPU это **в 20–75× медленнее CPU**. Поэтому при `device='gpu'` OCR **автоматически считается на CPU** (детекторы остаются на GPU) — это дефолт, он бит-в-бит точен и обычно быстрее чистого CPU.

### `pipeline.warmup(img_path=None)`

Каждая ONNX-сессия уже прогревается один раз при создании `Pipeline` (синтетический тензор
нужной формы) — первый реальный вызов `process_img()` после конструирования уже не «холодный».
`warmup()` — явный, документированный шаг для прогрева **всей** цепочки целиком (Python-код
пред/постобработки, deskew, разбивка на слова, роутинг OCR), который синтетический прогрев
модели-за-моделью не покрывает. Вызывайте один раз перед началом бенчмарка/боевой обработки
потока документов:

```python
pipeline = Pipeline(device="gpu", ocr="accurate")
pipeline.warmup("path/to/any/sample_document.jpg")  # реальный документ - полный прогрев
# или без аргумента - прогреет только этапы doctype/качество (без реального документа
# нельзя прогреть детекторы полей/OCR - синтетическое изображение классифицируется как 'NONE')
```

Есть экспериментальный флаг `ocr_gpu_batch=True`, батчующий слова в несколько GPU-вызовов фиксированной формы. После прогрева (первые несколько *разных* документов) это быстрее CPU, но измеримо меняет часть распознанного текста (~5–14% полей на реальных документах, зависит от движка) из-за особенностей архитектуры моделей. Включайте только после проверки на своих данных — подробности и цифры зафиксированы во внутреннем инженерном журнале проекта.

### `pipeline.process_img(img_path, *, ocr=True, get_doc_borders=True, find_text_fields=True, check_quality=True, low_quality=True, docconf=0.5, img_size=1500)`

- `img_path` — `str` / `pathlib.Path` / `np.ndarray`.
  **Важно:** если передаёте `np.ndarray`, он должен быть в **RGB** (как `PIL`/`cv2.cvtColor(img, COLOR_BGR2RGB)`), а не «сырой» BGR из `cv2.imread`.
- `ocr` — выполнять ли OCR;
- `check_quality` — считать ли метрики качества;
- `low_quality=True` — не прерываться на плохом качестве (иначе при бликах/размытии вернёт ранний результат);
- `img_size` — большая сторона ресайзится до этого размера.

Возвращает `PipelineResults`:

| свойство | тип | что |
|---|---|---|
| `.doctype` | `str` | тип документа (`'NONE'` если не распознан) |
| `.ocr` | `dict` \| `None` | распознанные поля (ключи зависят от типа документа) |
| `.quality` | `dict` | `Glare`, `Blur`, `PrintSpoofing`, `LCDSpoofing`, `DocConf` |
| `.full_report` | `dict` | всё вместе |
| `.timings` | `dict` | тайминги по стадиям + `total` |

## Быстрая интеграция для Claude

Если ты — ИИ-ассистент и тебя попросили «подключить RussianDocsOCR в этот проект»:

1. **Проверь окружение:** Python 3.10-3.12. Установи зависимости из `requirements2026.txt`
   (дефолт; используй старый `requirements.txt` только при конфликте версий в проекте-цели).
   Для GPU замени `onnxruntime` → `onnxruntime-gpu==1.21.1`.
2. **Сделай пакет импортируемым:** добавь корень репозитория в `sys.path` или скопируй
   каталог `document_processing/` (с `models/`) в проект. Убедись, что папка `models/`
   на месте — там бинарные `.onnx` (без них ничего не загрузится).
3. **Оберни в функцию** (готовый шаблон ниже) и вызывай из своего кода.
4. **Выбор режима:** по умолчанию `ocr='accurate'`, `device=None` (авто GPU→CPU). Для
   потоковой обработки на слабом железе — `ocr='fast'`.
5. **Не создавай `Pipeline` на каждый вызов** — это загрузка 12 моделей. Создай один раз,
   переиспользуй (потокобезопасность не гарантируется — по одному инстансу на процесс/поток).
6. **Изображения:** `np.ndarray` подавай в **RGB**.

Минимальная обёртка для встраивания:

```python
import sys
from functools import lru_cache

sys.path.insert(0, "/путь/к/RussianDocsOCR")   # шаг 2
from document_processing import Pipeline


@lru_cache(maxsize=1)
def _get_pipeline(ocr: str = "accurate", device=None):
    """Ленивая инициализация (модели грузятся один раз)."""
    return Pipeline(device=device, ocr=ocr)


def recognize(image_path: str, ocr: str = "accurate") -> dict:
    """Распознать документ РФ. Возвращает {'doctype', 'fields', 'quality'}."""
    p = _get_pipeline(ocr)
    r = p.process_img(image_path)
    return {
        "doctype": r.doctype,
        "fields": r.ocr or {},
        "quality": r.quality,
    }


if __name__ == "__main__":
    from pprint import pprint
    pprint(recognize("samples/DL_2011/1_CR_DL_2010.jpg"))
```

Обработка папки:

```python
from pathlib import Path

p = _get_pipeline("accurate")
for img in Path("input_docs").glob("*.jpg"):
    r = p.process_img(str(img))
    print(img.name, r.doctype, r.ocr)
```

## GPU

Библиотека сама добавляет DLL из `torch/lib` в путь поиска (Windows), чтобы onnxruntime
нашёл CUDA/cuDNN — поэтому если в окружении есть `torch` с CUDA, `device='gpu'` работает
без ручной настройки PATH. Проверка, что GPU реально доступен:

```python
import onnxruntime as ort
print(ort.get_available_providers())   # должен быть 'CUDAExecutionProvider'
```

Если провайдера нет — установлен CPU-`onnxruntime` (нужен `onnxruntime-gpu`) или не видны
CUDA/cuDNN DLL. При `device='gpu'` без рабочего CUDA onnxruntime молча откатится на CPU.

## Производительность: варианты запуска и рекомендации

Замерено на РТХ 4070 Ti Super + Intel i7 14-го поколения, среднее время на документ (полный
`process_img`, реальные образцы из `samples/`). OCR-движки (`accurate`/`fast`) — модели с
динамической шириной входа; детекторы (Borders/TextFields/DocTypeAngles/…) — фиксированного
размера. Это разное поведение на GPU и определяет рекомендации ниже.

### На CPU (`device='cpu'`)

| `ocr=` | ~время/документ | когда использовать |
|---|---|---|
| `'accurate'` (по умолч.) | ~800 мс | **Рекомендуется по умолчанию.** Лучшее качество, символьных ошибок почти нет (проверено на реальных загранпаспортах). |
| `'fast'` | ~710 мс | Небольшой выигрыш скорости. Кириллица сейчас на промежуточном чекпоинте (EdgeNext) — иногда обрезает последний символ слова (`ОБЛ`→`ОБЛ`, тестировалось). Латиница и цифры уже чистые. Использовать, если нужна скорость и это приемлемо, или подождать финальный чекпоинт cyrillic_fast. |

### На GPU (`device='gpu'`)

Детекторы получают **устойчивое ~5× ускорение** на GPU (фиксированный размер входа —
никаких компромиссов). OCR-движки — **по умолчанию всё равно считаются на CPU**, даже при
`device='gpu'` (см. ниже почему); задействовать GPU для OCR может только опциональный
батчинг.

| режим | ~время/документ | что происходит | рекомендация |
|---|---|---|---|
| `ocr='accurate'` (по умолч., `ocr_gpu_batch=False`) | **~510 мс** | детекторы на GPU, OCR автоматически на CPU | **Рекомендуется для GPU-развёртывания.** Быстрее чистого CPU, при этом бит-в-бit идентично `device='cpu'` — без компромиссов по точности. |
| `ocr='fast'` (по умолч.) | **~390 мс** | то же, OCR на CPU | Для максимальной пропускной способности при приемлемом текущем качестве кириллицы (см. таблицу CPU выше). |
| `ocr_gpu_batch=True` (опционально, `accurate`/`fast`) | ~490–570 мс после прогрева (холодный старт — до нескольких секунд) | все слова документа батчатся в GPU-вызовы фиксированной формы | **Экспериментально, не по умолчанию.** Меняет часть распознанного текста (~5–14% полей от CPU-эталона, зависит от движка) — используйте только после проверки на своих документах. |

Дополнительно, независимые стадии (4 проверки качества + определение границ; разбивка полей на
слова) теперь выполняются конкурентно в потоках — на изолированных замерах это даёт ещё
**~20–40%** к стадиям, где применимо (напр. quality+border-detection на GPU: 132→83 мс), поверх
цифр в таблице выше.

**Почему OCR не ускоряется на GPU «из коробки»:** `accurate`/`fast` принимают слова
переменной ширины; на CUDA-провайдере ONNX Runtime каждая новая ширина заново компилирует
граф — поштучная подача (как это происходит естественно) даёт задержку в **20–75× больше**,
чем на CPU. Библиотека обнаруживает это сама и просто считает OCR на CPU, оставляя детекторы
на GPU — специально настраивать ничего не нужно.

**Итоговая рекомендация:**
- **Есть GPU** → используйте `device='gpu'` с `ocr='accurate'` (дефолт) — лучший баланс скорости и точности, без ручной настройки.
- **Только CPU** → `ocr='accurate'` (дефолт) для качества, `ocr='fast'` для скорости при приемлемом текущем качестве кириллицы.
- **`ocr_gpu_batch=True`** — оставьте для частных случаев (проверенный высоконагруженный сценарий), не для нового кода по умолчанию.

## Диагностика

| симптом | причина / решение |
|---|---|
| `results.doctype == 'NONE'` | документ не распознан (не тот тип/сильный дефект кадра) |
| OCR не ускоряется при `device='gpu'` | **это норма**, не баг — см. [«Производительность»](#производительность-варианты-запуска-и-рекомендации): OCR намеренно считается на CPU по умолчанию |
| OCR работает медленно на CPU | попробуй `ocr='fast'` (см. таблицу производительности) |
| пустой/мусорный OCR на `np.ndarray` | подан BGR вместо RGB — конвертируй `cv2.cvtColor(img, cv2.COLOR_BGR2RGB)` |
| GPU не задействуется вообще (даже детекторы) | нет `CUDAExecutionProvider` (см. [GPU](#gpu)) |
