# RussianDocsOCR

Открытая библиотека для **распознавания документов граждан РФ** по одному изображению — фото с
телефона или скану. Специальное оборудование не нужно, всё работает на вашем компьютере, без
внешних сервисов.

- Код: [github.com/protei300/RussianDocsOCR](https://github.com/protei300/RussianDocsOCR)
- [**Вики**](https://github.com/protei300/RussianDocsOCR/wiki): устройство проекта, примеры подключения, частые вопросы
- Лицензия [**MIT**](LICENSE). Она распространяется и на код, и на **обученные модели**
  (около 275 МБ, скачиваются [отдельной командой](#установка)). Сторонние компоненты — в [`NOTICE`](NOTICE).
- Проект выполнен при поддержке Фонда содействия инновациям.

> Этот файл написан и для человека, и для ИИ-помощника (Claude). Раздел
> [«Быстрая интеграция для Claude»](#быстрая-интеграция-для-claude) — пошаговая инструкция, как
> подключить библиотеку к другому проекту за пару минут.

> **Нужен готовый сервис, а не библиотека?** В репозитории есть сервис с REST-интерфейсом и
> веб-страницей: документ ставится в очередь, в ответ приходит JSON с полями и координатами
> найденных областей, области рисуются поверх выпрямленного изображения. Один docker-образ работает
> и с видеокартой, и без неё. Главное в нём — **показать, как правильно вызывать библиотеку из
> сервиса**: она не рассчитана на несколько потоков сразу, загружает около 275 МБ моделей, а её
> результат живёт только до следующего вызова. Все эти ловушки в сервисе разобраны по пунктам.
> Описание: [`service/README.md`](service/README.md).
>
> Если сервис не должен хранить документы **вообще**, запустите его с
> `PROCESSING_MODE=memory`. Тогда документ разбирается прямо внутри запроса
> `POST /api/v1/recognize`, ответ уходит сразу, а память очищается: на диске и в журнале не
> остаётся ни снимка, ни прочитанных полей, ни имени файла. Так же работают порты на Go, .NET и
> Kotlin. Подробности — [`docs/in-memory.md`](docs/in-memory.md).

> **Собираетесь обрабатывать настоящие документы?** Прочитайте [`SECURITY.md`](SECURITY.md) до
> запуска. Коротко: обработка полностью локальная, наружу ничего не уходит, но **оператором
> персональных данных становитесь вы**, а снимок паспорта содержит биометрию (фотографию лица), и для
> неё закон требует отдельного основания. Там же перечислено, что и где сохраняется, чего программа
> **не** делает (нет TLS, нет шифрования на диске, нет удаления по сроку — для этого есть режим
> разбора в памяти без хранения), и список шагов для безопасного запуска. Своих персональных данных у проекта нет: точность измерялась внутри сети
> заказчика, а в репозитории лежат только обезличенные образцы
> ([`samples/README.md`](samples/README.md)).

> **Пишете не на Python?** Библиотека и сервис есть в **четырёх реализациях**: Python, Go, .NET и
> Kotlin/JVM. Это не приблизительные переводы: каждый шаг обработки в каждой реализации сверяется с
> Python до последней цифры на наборе контрольных документов. Обзор и сравнение —
> [`ports/README.md`](ports/README.md).

Все четыре сервиса отдают одинаковый REST-интерфейс и одну и ту же веб-страницу (`web/`), так что
для клиента они неотличимы. Для браузера и Node есть готовый клиент без зависимостей —
[`web/src/client/rdocs-client.ts`](web/src/client/rdocs-client.ts), а страница `/integration`
показывает подключение сайта к сервису на настоящих вызовах.

## Что умеет

По одному изображению библиотека:
- **находит документы в кадре** и вырезает каждый в полном разрешении: маленькие права на скане
  листа А4 читаются так же, как крупный снимок; `process_frame` читает все документы кадра сразу;
- определяет **тип документа** и поворот (на 90°, 180°, 270°) и разворачивает изображение;
- оценивает **качество**: блики, размытие, признаки снимка с экрана или распечатки;
- находит границы документа, исправляет перспективу и остаточный наклон;
- находит текстовые поля, делит их на слова и **читает текст** — кириллицу и латиницу;
- отмечает у каждого поля, **можно ли верить прочитанному**: сверяет с машиночитаемой зоной,
  контрольными цифрами, датами;
- показывает, **где каждое поле лежит на исходном снимке**, — чтобы подсветить его на фотографии
  пользователя.

**Поддерживаемые документы:**
- водительское удостоверение (2011–2019 и с 2020 года); оборот опознаётся, поля оборота пока не читаются;
- внутренний паспорт (1997–2011 и с 2011 года);
- страница прописки внутреннего паспорта: строки адреса и **штампы регистрации** — у каждого штампа
  свой адрес, видно, какую регистрацию снимает штамп «снят с учёта», и какая регистрация действующая;
- загранпаспорт (с биометрией с 2007 года, без неё с 2003 года);
- СНИЛС (с 1996 года);
- свидетельство о рождении (бланки 1998 и 2018 годов);
- свидетельство о регистрации ТС (бланки 1996 и 2019 годов, обе стороны), в том числе признак лизинга.

## Точность

Измерено на **50 000 внутренних паспортов РФ**. Это снимки, которые люди делали сами, подавая заявку
на кредит: телефон, посторонний фон, блики, наклон. Прогон шёл **внутри сети заказчика**: сами
документы нам не передавались, наружу выходили только итоговые числа, поэтому набор нельзя
опубликовать. Условия: видеокарта, короткая сторона снимка больше 900 пикселей.

| | |
|---|---|
| Определение типа документа | **99,01 %** |
| Поиск полей — точность / полнота | **98,4 % / 99,8 %** |
| Чтение русского текста на фоне бланка | **не ниже 97 %** по всем полям |

Сравнение распознавания текста с открытыми движками на том же наборе (средняя мера качества):

| Движок | Русский | Английский |
|---|---|---|
| **RussianDocs** | **0,9745** | **0,9721** |
| PaddleOCR | 0,92 | 0,96 |
| EasyOCR | 0,8044 | 0,9133 |
| Tesseract OCR | 0,4118 | 0,5051 |

Заметный отрыв — на **русском**. На английском PaddleOCR почти вровень (0,96 против 0,9721), и на
одном закрытом наборе такая разница может быть случайной.

Мера — `1 − среднее нормированное расстояние Левенштейна` по всем полям; расстояние делится на
длину более длинной из двух строк (эталона или прочитанного). **Это не доля ошибочных символов
(CER)**, и сравнивать её с числами CER из других проектов нельзя. Формула, причины выбора и
оговорки — в [`docs/accuracy.md`](docs/accuracy.md).

⚠️ **Эти числа получены на прежнем поколении моделей чтения, не на нынешних.** Нынешние по
внутренним замерам заметно лучше (доля ошибочных символов 0,123 → 0,062), но на этих 50 000
документах их не прогоняли, а повторить прогон можно только там же, внутри сети заказчика. То есть
опубликованное — нижняя граница на старых моделях, а не «стало лучше на столько-то».

Ещё две оговорки, без которых числа легко прочитать шире, чем следует:
- в выборке паспорта одного типа, поэтому 99,01 % — это «узнать паспорт», а не путаница между
  разными типами документов;
- **хуже всего читается место рождения**: свободный текст с сокращениями и переносами. Именно оно
  решает, сколько документов придётся проверять человеку, а среднее по полям это прячет.

Это замеры самих разработчиков на закрытом наборе из настоящих документов, проверить их со стороны
нельзя. Чего в этих числах пока **нет** (размер выборки, версия моделей, разбивка по полям) —
там же, в `docs/accuracy.md`. Проверить на своих данных: `python scripts/eval_quality.py`.

## Требования

- **Python 3.10–3.12.**
- Зависимости — **[`requirements.txt`](requirements.txt)**: проверенный набор (numpy 2.2,
  onnxruntime 1.21, opencv 4.12, scikit-learn 1.7 и другие). Набор проверен целиком в чистом
  окружении: все тесты и `process_img` на процессоре и на видеокарте дают одинаковый результат.
  До 4.6.0 этот файл назывался `requirements2026.txt`, старое имя пока работает. Прежний набор
  2023 года (numpy 1.26, onnxruntime 1.16) удалён: в нём были известные уязвимости. Если он всё же
  нужен, возьмите его из версий до 4.6.0.
- Для **видеокарты**: вместо `onnxruntime` установить `onnxruntime-gpu` той же версии и иметь
  CUDA и cuDNN (для RTX 40xx — CUDA 12.x и cuDNN 9). Подробнее — в разделе [GPU](#gpu).

## Установка

### Как пакет pip (только библиотека)

```bash
pip install git+https://github.com/protei300/RussianDocsOCR.git
rdocs-fetch-models   # скачает модели (около 275 МБ) в установленный пакет и проверит контрольные суммы
```

Импорт — `from document_processing import Pipeline`. Обёртки `russian_docs_ocr.` из версий 3.x
больше нет. В пакет входит только библиотека; сервис, порты на другие языки и сверка портов
живут в репозитории. Для видеокарты после установки:
`pip uninstall onnxruntime -y && pip install onnxruntime-gpu==1.21.1`.

### Из копии репозитория (разработка, сервис, тесты)

```bash
# 1. получить код (репозиторий лёгкий — моделей в нём нет)
git clone https://github.com/protei300/RussianDocsOCR.git
cd RussianDocsOCR

# 2. скачать модели (около 275 МБ); контрольные суммы проверяются
python scripts/fetch_models.py

# 3. зависимости (для процессора)
pip install -r requirements.txt
#    для видеокарты: pip uninstall onnxruntime -y && pip install onnxruntime-gpu==1.21.1
```

**Почему модели не в git.** Это сотни мегабайт файлов, которые скачивались бы при каждом
клонировании и навсегда остались бы в истории. Вместо этого состав набора записан в
[`document_processing/models.lock.json`](document_processing/models.lock.json): путь, размер и
контрольная сумма SHA-256 каждого из 33 файлов. Сами файлы лежат во вложениях выпусков на GitHub.
Лицензия та же, MIT.

Загрузчик написан только на стандартной библиотеке Python, поэтому работает до `pip install`.
Он качает только недостающие и повреждённые файлы, сверяет контрольные суммы и записывает файл
целиком или не записывает вовсе — недокачанная модель не превратится в непонятную ошибку чтения.

```bash
python scripts/fetch_models.py --check   # проверить, что все модели на месте и целы
python scripts/fetch_models.py --force   # скачать всё заново
```

**Закрытая сеть.** Скопируйте файлы моделей на свой сервер и укажите
`RDOCS_MODELS_URL=https://ваш.сервер/rdocs/models/` — код менять не нужно. Если модели уже лежат
в другом месте, путь к ним задаёт `RDOCS_MODELS_ROOT` (ту же переменную читают порты на Go, .NET и
Kotlin).

Чтобы использовать библиотеку из своего проекта без установки пакетом, каталог
`document_processing/` (вместе с `models/`) должен быть доступен для импорта. Проще всего
добавить корень репозитория в `sys.path`:

```python
import sys
sys.path.insert(0, "/путь/к/RussianDocsOCR")
from document_processing import Pipeline
```

Или скопировать каталог `document_processing/` (вместе с `models/`) в свой проект.

## Быстрый старт

```python
from document_processing import Pipeline

# device=None — видеокарта, если доступна CUDA, иначе процессор
# ocr='accurate' (по умолчанию) или 'fast'
pipeline = Pipeline(device=None, ocr='accurate')

results = pipeline.process_img('path/to/passport.jpg')

print(results.doctype)        # например, 'INTPASSPORT_2011'
print(results.ocr)            # {'Last_name_ru': 'ИВАНОВ', 'First_name_ru': 'ИВАН', ...}
print(results.field_checks)   # {'Last_name_ru': {'status': 'verified', ...}, ...}
print(results.quality)        # {'Glare': 'good', 'Blur': 'good', 'DocConf': 0.98, ...}
print(results.timings)        # время каждого шага, {'total': 0.8, ...}
```

Весь результат одним словарём:

```python
report = results.full_report   # {'DocType': ..., 'OCR': ..., 'Quality': ..., 'Timings': ...}
```

## Описание вызовов

### `Pipeline(model_format='ONNX', device=None, ocr='accurate', verbose=False, ocr_gpu_batch=False)`

| параметр | значения | что делает |
|---|---|---|
| `model_format` | `'ONNX'` (рекомендуется), `'OpenVINO'` | какой **движок** исполняет модели поиска и классификации. Файлы моделей одни и те же (`.onnx`), OpenVINO читает их напрямую. Чтение текста всегда идёт через onnxruntime |
| `device` | `None`, `'cpu'`, `'gpu'` | `None` — видеокарта, если onnxruntime её видит, иначе процессор. Про чтение текста на видеокарте — ниже |
| `ocr` | `'accurate'`, `'fast'` | модель чтения текста (ниже) |
| `verbose` | `bool` | печатать ход загрузки моделей |
| `ocr_gpu_batch` | `bool`, по умолчанию `False` | ОПЫТНЫЙ режим: чтение текста пачками на видеокарте, см. ниже |

Другие параметры: `detect_documents=True` (сначала искать документы в кадре; `False` — читать кадр
целиком), `page_registration=True` (выпрямлять страницы паспорта по шаблону бланка),
`card_registration=True` (выпрямлять СТС по шаблону бланка). Полное описание — в docstring
`Pipeline.__init__`.

> **Если вызываете модули по отдельности.** У `Pipeline` движок задаётся через `model_format`, а у
> отдельных модулей это два разных аргумента: `model_format` выбирает **папку с моделью**,
> `runtime` — **движок исполнения**. Для OpenVINO передавайте `runtime`, иначе загрузится
> onnxruntime:
> ```python
> Blur(model_format='ONNX', runtime='OpenVINO', device='cpu')
> ```
> Движок выбирается так: аргумент `runtime` → ключ `"Runtime"` в `model.json` → расширение файла.

**Модели чтения текста:**
- `'accurate'` (по умолчанию) — MobileNetV4, наибольшая точность;
- `'fast'` — EdgeNext, быстрее, точность немного ниже.

> **Удалено в 3.0.0:** `ocr='legacy'` (первые модели rus и eng+nums), флаг `fv_ocr` и разбор
> регулярными выражениями. Старая модель чаще путала символы, а путь FV проигрывал обычному
> пошаговому разбору; держали их только ради совместимости. `ocr='legacy'` теперь вызывает
> `ValueError` с этим объяснением.

**Видеокарта и чтение текста.** Обе модели чтения принимают слово любой ширины. На видеокарте
ONNX Runtime для каждой новой ширины заново собирает граф, и по одному слову это **в 20–75 раз
медленнее процессора**. Поэтому при `device='gpu'` текст по умолчанию **читается на процессоре**, а
поиск и классификация остаются на видеокарте. Результат при этом в точности такой же, как на
процессоре, а работа в целом обычно быстрее.

### `pipeline.warmup(img_path=None)`

Каждая модель один раз прогревается уже при создании `Pipeline` (на искусственных данных нужной
формы), так что первый настоящий вызов `process_img()` не будет «холодным». `warmup()` прогревает
**всю цепочку** целиком — подготовку и разбор данных, выпрямление, деление на слова, выбор модели
чтения, — чего прогрев по одной модели не покрывает. Вызывайте один раз перед замером скорости или
перед обработкой потока документов:

```python
pipeline = Pipeline(device="gpu", ocr="accurate")
pipeline.warmup("path/to/any/sample_document.jpg")  # настоящий документ — полный прогрев
# без аргумента прогреются только определение типа и качества: по искусственной
# картинке тип не определится ('NONE'), и до полей и чтения дело не дойдёт
```

Опытный режим `ocr_gpu_batch=True` собирает слова документа в несколько вызовов видеокарты
постоянной формы. После прогрева (несколько *разных* документов) это быстрее процессора, но
заметно меняет часть прочитанного текста (около 5–14 % полей на настоящих документах, зависит от
модели) из-за устройства самих моделей. Включайте только после проверки на своих данных.

### `pipeline.process_img(img_path, *, ocr=True, get_doc_borders=True, find_text_fields=True, check_quality=True, low_quality=True, docconf=0.5, img_size=1500)`

- `img_path` — `str`, `pathlib.Path` или `np.ndarray`.
  **Важно:** `np.ndarray` должен быть в порядке цветов **RGB** (как у `PIL` или после
  `cv2.cvtColor(img, cv2.COLOR_BGR2RGB)`), а не BGR, который возвращает `cv2.imread`.
- `ocr` — читать ли текст;
- `check_quality` — оценивать ли качество;
- `low_quality=True` — не останавливаться при плохом качестве (иначе при бликах или размытии
  вернётся ранний результат);
- `img_size` — до какого размера уменьшать большую сторону.

`pipeline.process_frame(...)` читает **все** документы кадра и, например, связывает две стороны
одного СТС; `process_img` читает самый крупный.

Возвращает `PipelineResults`:

| свойство | тип | что внутри |
|---|---|---|
| `.doctype` | `str` | тип документа (`'NONE'`, если не определён) |
| `.ocr` | `dict` или `None` | прочитанные поля (набор зависит от типа документа) |
| `.field_checks` | `dict` | у каждого поля из `.ocr`: `verified` — проверка сошлась, `mismatch` — почти наверняка ошибка чтения, `unchecked` — проверить нечем. Сами значения в `.ocr` не исправляются. Список проверок — [`docs/validation-checks.md`](docs/validation-checks.md) |
| `.quality` | `dict` | `Glare`, `Blur`, `PrintSpoofing`, `LCDSpoofing`, `DocConf` |
| `.documents` | `list` | найденные в кадре документы с рамками; `.document_box` — рамка прочитанного |
| `.registration_stamps` | `list` | штампы регистрации на странице прописки, от самого свежего: вид, рамка на снимке, свои строки и адрес, `cancels`, `current` |
| `.leasing` | `dict` или `None` | признак лизинга у СТС |
| `.full_report` | `dict` | всё вместе |
| `.timings` | `dict` | время каждого шага и `total` |
| `.field_quads` | `dict` или `None` | где каждое прочитанное поле лежит **на исходном снимке**: `метка → [четырёхугольник (4, 2), …]` в пикселях изображения, переданного в `process_img`, по одному на найденную рамку, сверху вниз |
| `.word_quads` | `dict` или `None` | то же для слов |
| `.address_line_quads` | `list` или `None` | строки адреса на странице прописки (`INTPASSPORTADDR`), на снимке |
| `.to_input(points)` | `ndarray` или `None` | любые точки обработанного изображения `(N, 2)` → на исходный снимок |

Четырёхугольники нужны, чтобы показать человеку поле на его фотографии, а не на внутреннем
изображении библиотеки: то уменьшено, повёрнуто, выпрямлено по страницам и склеено, и каждый из
этих шагов умеет вернуть точку назад. Если хотя бы для одного шага обратный путь неизвестен, все
четырёхугольники этого вызова — `None`: рамка, которая молча легла не туда, хуже её отсутствия.

```python
quads = results.field_quads
if quads is not None:
    for label, boxes in quads.items():
        for quad in boxes:                       # (4, 2), пиксели исходного снимка
            cv2.polylines(img, [quad.round().astype(np.int32)], True, (255, 0, 0), 2)
```

## Быстрая интеграция для Claude

Если ты ИИ-помощник и тебя попросили «подключить RussianDocsOCR к этому проекту»:

1. **Проверь окружение:** Python 3.10–3.12. Установи зависимости из `requirements.txt`
   (до 4.6.0 он назывался `requirements2026.txt`).
   Для видеокарты замени `onnxruntime` на `onnxruntime-gpu==1.21.1`.
2. **Сделай пакет доступным для импорта:** добавь корень репозитория в `sys.path` или скопируй
   каталог `document_processing/` (с `models/`) в проект. Проверь, что в `models/` есть файлы
   `.onnx` — без них ничего не загрузится (`python scripts/fetch_models.py --check`).
3. **Оберни в функцию** (шаблон ниже) и вызывай из своего кода.
4. **Режим:** по умолчанию `ocr='accurate'`, `device=None` (видеокарта, если есть). Для потока
   документов на слабом железе — `ocr='fast'`.
5. **Не создавай `Pipeline` на каждый вызов** — это загрузка всех моделей. Создай один раз и
   используй повторно. Один экземпляр не рассчитан на несколько потоков: заводи по экземпляру на
   процесс или поток.
6. **Изображения:** `np.ndarray` подавай в **RGB**.

Минимальная обёртка:

```python
import sys
from functools import lru_cache

sys.path.insert(0, "/путь/к/RussianDocsOCR")   # шаг 2
from document_processing import Pipeline


@lru_cache(maxsize=1)
def _get_pipeline(ocr: str = "accurate", device=None):
    """Создаётся при первом вызове, модели загружаются один раз."""
    return Pipeline(device=device, ocr=ocr)


def recognize(image_path: str, ocr: str = "accurate") -> dict:
    """Распознать документ РФ. Возвращает {'doctype', 'fields', 'checks', 'quality'}."""
    p = _get_pipeline(ocr)
    r = p.process_img(image_path)
    return {
        "doctype": r.doctype,
        "fields": r.ocr or {},
        "checks": r.field_checks,
        "quality": r.quality,
    }


if __name__ == "__main__":
    from pprint import pprint
    pprint(recognize("samples/DL_2011/1_CR_DL_2010.jpg"))
```

Обработка папки:

```python
from pathlib import Path

p = _get_pipeline("accurate")
for img in Path("input_docs").glob("*.jpg"):
    r = p.process_img(str(img))
    print(img.name, r.doctype, r.ocr)
```

## GPU

В Windows библиотека сама добавляет библиотеки из `torch/lib` в путь поиска, чтобы onnxruntime
нашёл CUDA и cuDNN. Поэтому если в окружении есть `torch` с поддержкой CUDA, `device='gpu'`
работает без ручной настройки PATH. Проверить, что видеокарта доступна:

```python
import onnxruntime as ort
print(ort.get_available_providers())   # в списке должен быть 'CUDAExecutionProvider'
```

Если его нет, значит, установлен `onnxruntime` без поддержки видеокарты (нужен `onnxruntime-gpu`)
или не найдены библиотеки CUDA и cuDNN. Без рабочей CUDA при `device='gpu'` onnxruntime молча
перейдёт на процессор.

## Производительность: варианты запуска и рекомендации

Замерено на RTX 4070 Ti Super и Intel i7 14-го поколения; среднее время на документ (весь
`process_img`, образцы из `samples/`). Модели чтения (`accurate`, `fast`) принимают слово любой
ширины, а модели поиска и классификации — изображение постоянного размера. Из-за этой разницы они
по-разному ведут себя на видеокарте, отсюда и рекомендации.

### На процессоре (`device='cpu'`)

| `ocr=` | время на документ | когда выбирать |
|---|---|---|
| `'accurate'` (по умолчанию) | около 800 мс | **Рекомендуется.** Лучшее качество, путаницы символов почти нет (проверено на настоящих загранпаспортах). |
| `'fast'` | около 710 мс | Немного быстрее. Модель кириллицы пока промежуточная и иногда теряет последнюю букву слова; латиница и цифры читаются чисто. Выбирайте, если важна скорость и это допустимо. |

### На видеокарте (`device='gpu'`)

Поиск и классификация на видеокарте **примерно в 5 раз быстрее** — без потерь, у них постоянный
размер входа. Чтение текста **по умолчанию всё равно идёт на процессоре** (почему — ниже);
использовать видеокарту для чтения может только опытный режим.

| режим | время на документ | что происходит | рекомендация |
|---|---|---|---|
| `ocr='accurate'` (по умолчанию) | **около 510 мс** | поиск на видеокарте, чтение на процессоре | **Рекомендуется для видеокарты.** Быстрее, чем только процессор, и результат в точности как при `device='cpu'`. |
| `ocr='fast'` | **около 390 мс** | то же | Для наибольшей пропускной способности, если устраивает нынешнее качество кириллицы (см. выше). |
| `ocr_gpu_batch=True` | 490–570 мс после прогрева (первые вызовы — до нескольких секунд) | все слова документа читаются пачками на видеокарте | **Опытный режим, не по умолчанию.** Меняет часть прочитанного текста (около 5–14 % полей), включайте только после проверки на своих документах. |

Независимые шаги — четыре оценки качества и поиск границ, а также деление полей на слова —
выполняются параллельно. На отдельных замерах это ускоряет такие шаги ещё на **20–40 %**
(например, качество и границы на видеокарте: 132 → 83 мс) поверх чисел в таблице.

**Почему чтение текста не ускоряется на видеокарте само.** Модели `accurate` и `fast` принимают
слова разной ширины; на видеокарте ONNX Runtime для каждой новой ширины заново собирает граф, и
чтение по одному слову выходит **в 20–75 раз медленнее**, чем на процессоре. Библиотека учитывает
это сама: читает текст на процессоре, а поиск оставляет на видеокарте. Настраивать ничего не нужно.

**Итог:**
- **Есть видеокарта** → `device='gpu'` и `ocr='accurate'` (по умолчанию): лучшее сочетание
  скорости и точности.
- **Только процессор** → `ocr='accurate'` ради качества, `ocr='fast'` ради скорости.
- **`ocr_gpu_batch=True`** — только для отдельных проверенных случаев с большой нагрузкой.

## Диагностика

| что видите | причина и что делать |
|---|---|
| `results.doctype == 'NONE'` | документ не опознан: не тот тип или сильно испорченный кадр |
| при `device='gpu'` чтение текста не ускоряется | **так и задумано** — см. [«Производительность»](#производительность-варианты-запуска-и-рекомендации): по умолчанию текст читается на процессоре |
| чтение медленное на процессоре | попробуйте `ocr='fast'` |
| пустой или бессмысленный текст при подаче `np.ndarray` | подан BGR вместо RGB: `cv2.cvtColor(img, cv2.COLOR_BGR2RGB)` |
| видеокарта не используется совсем | нет `CUDAExecutionProvider`, см. [GPU](#gpu) |
| у поля `field_checks[...]['status'] == 'mismatch'` | прочитанное значение не сошлось с проверкой — скорее всего, ошибка чтения; значение для сравнения лежит в `checks[...]['reference']` |

## Версии

Нумерация по правилам семантического версионирования (`MAJOR.MINOR.PATCH`).

- Версия записана в одном месте — `__version__` в `document_processing/__init__.py`.
- Изменения каждой версии — в [`CHANGELOG.md`](CHANGELOG.md).
- Выпуск отмечается тегом git `vX.Y.Z`.

Набор моделей нумеруется **отдельно** от кода (теги `models-<набор>`, список файлов —
`document_processing/models.lock.json`), см. [`docs/models-release.md`](docs/models-release.md).

> **Заранее предупреждаем.** В версии **6.0.0** из истории репозитория будут удалены старые файлы
> моделей версий 3.x и раньше (около 470 МБ, которые сейчас лежат в `.git` без пользы). Хеши
> коммитов изменятся, копии репозитория придётся склонировать заново; выпуски и файлы моделей
> останутся. Подробности и обсуждение — [issue #11](https://github.com/protei300/RussianDocsOCR/issues/11).

Порядок выпуска:
1. Обновить `__version__`.
2. Добавить раздел в `CHANGELOG.md`.
3. `git tag vX.Y.Z && git push origin vX.Y.Z`.
