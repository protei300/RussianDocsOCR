# Разбор в памяти (`PROCESSING_MODE=memory`)

Режим для внедрений, где сервис не должен хранить персональные данные **вообще**:
документ пришёл через API, разобран в памяти, ответ ушёл, память явно очищена. На диске
и в логах не остаётся ни картинки, ни распознанных полей, ни имени файла, ни типа
документа. В интерфейсе видно только, *что* что-то разбиралось, — провалиться внутрь
нельзя, потому что внутри ничего нет.

Нормативный контракт для портов (Go, .NET, Kotlin) — [`ports/MEMORY.md`](../ports/MEMORY.md),
проверка чёрным ящиком — [`conformance/memory_contract.py`](../conformance/memory_contract.py).

## Как включить

```bash
PROCESSING_MODE=memory DATA_DIR=... JWT_SECRET=... DEFAULT_API_KEY=... \
  python -m uvicorn service.main:app --host 0.0.0.0 --port 8002 --workers 1
```

| `PROCESSING_MODE` | Режим |
|---|---|
| не задан, пусто | `stored` — как было всегда |
| `stored` | `stored` |
| `memory` | `memory` |
| **любое другое значение** (опечатка) | `memory`, причина видна в логе при старте и на `/status` |

Опечатка трактуется в сторону приватности — в отличие от `AUTH_MODE`. Кто написал
`memroy`, просил не хранить документы; молча начать их хранить — нарушить единственное
обещание этой настройки. Переключателя в интерфейсе нет и не будет: админ на веб-странице
не должен иметь возможность включить хранение обратно.

Связанные переменные: `RECOGNIZE_WAIT_SEC` (30) — сколько запрос ждёт свободный конвейер,
прежде чем ответить 503; `RECOGNITION_JOURNAL_MAX` (5000) — длина журнала в памяти;
`MAX_UPLOAD_MB` — как и для загрузок.

## Что меняется

| | `stored` | `memory` |
|---|---|---|
| `/api/v1/documents/*` | как было | **404** до чтения тела запроса |
| фоновый воркер, очередь | работают | выключены (модели всё равно грузятся и греются) |
| сид-документы | по настройке | никогда |
| `POST /api/v1/recognize` | есть | есть — единственный вход |
| `GET /api/v1/recognitions` | есть | есть |
| пользователи, ключи, настройки, статус, логи | как было | как было |

## API

```bash
# картинка — тело запроса
curl -H "X-API-Key: $KEY" -H "Content-Type: image/jpeg" \
     --data-binary @photo.jpg http://host:8002/api/v1/recognize

# или multipart, поле file; ?images=1 — вернуть выпрямленный канвас base64 PNG
curl -H "X-API-Key: $KEY" -F "file=@photo.jpg" "http://host:8002/api/v1/recognize?images=1"
```

Доступ: API-ключ или пользователь с ролью operator и выше. Ответ — тот же JSON, что у
сохранённого документа (`doc_type`, `fields`, `boxes`, `quality`, `address`, …), плюс
`"stored": false`, без `id` и ссылок; заголовок `Cache-Control: no-store`. Отказы:
413 (больше лимита), 415 (PDF / не картинка), 400 (пусто), 422 (не декодируется),
503 + `Retry-After` (все конвейеры заняты или модели ещё грузятся), 504, 500.

Журнал: `GET /api/v1/recognitions` (роль viewer и выше) — только
`{id, at, outcome, status_code, processing_ms, stored:false}`. Хранится в памяти процесса,
теряется при перезапуске. В лог пишется одна строка на запрос:
`[API] recognize: outcome=recognised status=200 ms=639`.

## Интерфейс

В режиме `memory` страница «Documents» показывает плашку «Memory mode — documents are not
stored», журнал разборов (строки не кликабельны) и кнопку «Recognise document». Результат
показывается один раз в диалоге; при закрытии диалога всё (файл, превью, канвас, поля)
выбрасывается, object-URL отзываются. В `localStorage` ничего не пишется. Запросов к
`/documents` интерфейс в этом режиме не делает.

В режиме `stored` есть та же кнопка «Recognise without storing», а журнал появляется под
списком документов, когда в нём что-то есть.

## Что именно очищается — и чего обещать нельзя

Очищается (перезаписывается нулями, затем освобождается):

* буфер тела запроса и байты картинки;
* декодированные пиксели (BGR и RGB);
* состояние конвейера после документа — `pipeline.results` и `_mrz_zone` со всеми
  массивами внутри (~16 МБ на документ, раньше жили до следующего вызова) — внутри аренды
  конвейера, до того как его получит следующий запрос;
* PNG канваса.

Тело запроса **не попадает на диск**: обычный `UploadFile` FastAPI сбрасывает файл больше
1 МБ во временный файл ещё до нашего кода, поэтому `/recognize` читает поток сам и разбирает
multipart в памяти. По той же причине в режиме `memory` маршруты `/documents` отвечают 404
в middleware, не читая тело.

**Чего не обещаем.** Строки неизменяемы — в Python, Go, .NET и JVM: распознанный текст и
сериализованный JSON освобождаются, и память переиспользуется, но не перезаписывается.
Своп ОС, дампы памяти процесса, логи обратного прокси и TLS-терминатора, кэши клиента —
вне сервиса; их настраивает тот, кто разворачивает. Если нужен этот уровень — шифрованный
своп / отключённые core dump'ы и прокси без логирования тел.

## Проверка

```bash
python -m pytest tests/service/test_recognize.py -v      # 17 быстрых + 1 на реальных моделях
python -m conformance.memory_contract --port python      # чёрный ящик, 11 проверок
```

Тесты доказывают: на диск не пишется ни байта (в т. ч. multipart > 1 МБ при запрещённых
временных файлах), буферы обнулены, состояние конвейера вычищено и при ошибке, веса не
тронуты, в логе нет ни типа документа, ни текста исключения. Каждый тест проверен
мутацией — удаление соответствующей строки кода его валит.
