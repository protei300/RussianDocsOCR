# Слияние ветки `Service` в `main` — записка для того, кто будет мержить

Адресовано релиз-менеджеру (Виталий) и ассистенту, который будет ему помогать.
Написано автором ветки: здесь то, что не видно из диффа, и то, о чём диффу не
принято сообщать.

**Дата подготовки:** 2026-08-03. Ветка отведена от `main` (3.0.2).

---

## Что в ветке

Асинхронный REST-сервис поверх библиотеки плюс веб-интерфейс. Полная
документация — [`service/README.md`](../service/README.md); краткие правила для
ассистента — во внутренних инструкциях мейнтейнера (не публикуются).

Новое (ничего из этого не существует в `main`):

| Путь | Что |
|---|---|
| `service/` | бэкенд: FastAPI, воркер, хранилище, слой интеграции с библиотекой |
| `web/` | Vue 3.5 + TS SPA |
| `tests/service/` | тесты сервиса (в том числе 45 параметризованных по бэкендам хранилища) |
| `Dockerfile`, `.dockerignore` | один образ для GPU и CPU |
| `requirements-service.txt` | зависимости сервиса, отдельно от библиотечных |
| `docs/service-merge-notes.md` | этот файл |

**Состояние: ветка закоммичена и запушена, четыре коммита поверх `main` (3.0.2).**
Разбивка сделана намеренно так, чтобы спорную часть можно было не брать:

| # | Коммит | Что делать |
|---|---|---|
| 1 | `document_processing: fix Windows-only path separators` | **брать** — без него библиотека не работает на Linux |
| 2 | `Add reference web service: async REST + Vue UI…` | брать целиком; библиотеку не трогает |
| 3 | `docs: service documentation and merge notes` | брать |
| 4 | `pipeline: disable FMS dictionary lookup` | **решать отдельно** — единственный коммит, меняющий распознанный текст |
| 5 | `Melnikov: handwritten address research…` | **не брать** — исследовательский поток ветки `dev`, к сервису отношения не имеет |

Коммит 4 идёт последним именно поэтому: `git cherry-pick` первых трёх даёт
работающий сервис без изменения поведения распознавания.

⚠️ **Но есть связь между 2 и 4.** Фикстуры `service/seed_data/` сгенерированы
**после** отключения ФМС, то есть в них `Issue_organization_ru` записан как
«…ОБЛАСТИ», а не «…ОБЛ.». Если взять коммит 2 без коммита 4, сид-документы в логе
будут показывать текст, отличающийся от того, что даст живой прогон того же файла.
Расхождение косметическое и только в сид-данных, лечится одной командой:

```bash
python service/tools/build_seed_data.py
```

## ⚠️ Главное: в ветке есть три правки библиотеки, и их нельзя просто выкинуть

Изначальное условие было «библиотеку не трогаем, ветка не расходится с `main`».
Оно выдержано не полностью, и осознанно. Правки:

```
document_processing/ctc/__init__.py       |  8 +++++++-
document_processing/pipeline/pipeline.py  | 33 +++++++++++++++++---------
document_processing/processing/models.py  | 10 +++++++++-
```

### 1-2. Пути с обратным слэшем — **обязательны, это баг библиотеки**

`ctc/__init__.py` собирал путь как `joinpath(r'dictionary\fms_unit.csv')`, а
`processing/models.py` склеивал `working_dir / 'resources\centers.npz'` из
`model.json`. На POSIX обратный слэш — обычный символ имени файла, а не
разделитель, поэтому:

- `import document_processing` падал с `FileNotFoundError: .../ctc/dictionary\fms_unit.csv`;
- `DocTypeAngles` не конструировался.

То есть **библиотека не работала на Linux вообще**. На Windows работала годами,
поэтому это не проявлялось. Обнаружено только при сборке докер-образа.

Нормализация сделана в коде (`.replace('\\', os.sep)`), а не правкой артефактов:
обе конвенции продолжают работать и ни одну модель не надо перевыпускать. На
Windows изменение — no-op по построению (`os.sep` там `\`), и это проверено
полным прогоном тестов на Windows.

**Эти две правки полезны сами по себе, независимо от сервиса.** Разумно взять их
в `main` (или в `dev`) отдельным коммитом даже если сервис мержится позже.

### 3. Отключён поиск по словарю ФМС — **это изменение поведения распознавания, требует вашего решения**

`Pipeline._fix_fms` превращён в no-op. Раньше он переписывал
`Issue_organisation_code` / `Issue_organization_ru` по словарю ФМС.

Почему отключено — по прямому указанию заказчика после разбора:

- **Цена.** При точном совпадении кода поиск O(1) и ~1 мс. Но одна ошибочно
  прочитанная цифра уводит в фолбэк, который перебирает все ~16k записей через
  `difflib`, считая `SequenceMatcher.ratio()` для полной строки *и каждого слова*
  запроса. Замерено в живом прогоне: **5109 мс на один вызов**. Именно из-за
  этого сэмпл `INTPASSPORT_1997/15_CR_INTPASSPORT_2001.jpg` обрабатывался
  3.8 с против ~0.4 с у всех остальных.
- **Обоснованность.** На фолбэке словарь не *исправляет* код, а **заменяет** его
  кодом того подразделения, чьё название лучше совпало. Одна перепутанная цифра
  становится уверенным, правильно оформленным, но чужим кодом.

**Что это меняет в выводе:**

| Поле | Было | Стало |
|---|---|---|
| `Issue_organization_ru` | «УМВД РОССИИ ПО ТОМСКОЙ **ОБЛ.**» (нормализовано по словарю) | «УМВД РОССИИ ПО ТОМСКОЙ **ОБЛАСТИ**» (как прочитал OCR) |
| `Issue_organisation_code` при ошибке OCR | подменялся на код из словаря (иногда верно, иногда нет) | остаётся тем, что прочитал OCR |

Регрессия качества по `samples/` GT при этом остаётся в пороге:
`RUN_QUALITY=1 pytest tests/test_quality.py` — 4 passed.

**Варианты для релиза**, если отключение нежелательно в `main`:

1. Взять как есть (решение заказчика зафиксировано в
   внутреннем журнале мейнтейнера).
2. Вернуть словарь и ускорить фолбэк. Строго эквивалентная оптимизация была
   написана и отброшена по указанию заказчика («не нужно его делать совсем»): она
   отсекала кандидатов по собственным верхним границам `difflib`
   (`real_quick_ratio`/`quick_ratio`), переиспользовала кэш `b2j` через
   `set_seq1` и обходила кандидатов по близости длин, давая **бит-в-бит тот же**
   результат включая разрешение ничьих. В репозитории её нет — при желании
   восстанавливается по этому описанию.
3. Сделать переключателем `Pipeline(fms_lookup=...)`. Не сделано, чтобы не
   расширять публичный API библиотеки без запроса.

**Не мержьте пункт 3 молча.** Это единственная правка в ветке, которая меняет
распознанный текст.

## Порядок слияния

Ветка не коммичена, поэтому разумнее не мержить её целиком, а разложить на
осмысленные коммиты. Предлагаемая последовательность — от «безусловно полезного»
к «требующему решения»:

```bash
# 1. Кросс-платформенные фиксы библиотеки. Полезны сами по себе.
git add document_processing/ctc/__init__.py document_processing/processing/models.py
git commit -m "document_processing: fix Windows-only path separators (library did not import on Linux)"

# 2. Сервис. Самодостаточен, библиотеку не трогает.
git add service/ web/ tests/service/ requirements-service.txt Dockerfile .dockerignore
git commit -m "Add reference web service (FastAPI + Vue) demonstrating library integration"

# 3. Документация.
git add CLAUDE.md docs/service-merge-notes.md docs/progress-log.md
git commit -m "docs: service documentation and merge notes"

# 4. ОТДЕЛЬНО и осознанно — см. раздел выше.
git add document_processing/pipeline/pipeline.py
git commit -m "pipeline: disable FMS dictionary lookup (3.3-5.1s worst case, unsound fallback)"
```

В ветке есть **пятый коммит**, не относящийся к сервису — исследование по
распознаванию рукописной прописки (поток ветки `dev`):

```
Melnikov/Text_fields/build_gar_dictionary.py
Melnikov/Text_fields/gt_pipeline/
Melnikov/Text_fields/ocr_v2_reference/
Melnikov/Text_fields/train_addr_hw_crnn.py
document_processing/ctc/gar_functions.py      # ← не подключён к пайплайну, задел на будущее
```

Он оказался здесь только потому, что лежал в том же рабочем дереве, и закоммичен,
чтобы не потеряться. **В `main` его переносить не нужно.** Ничего из этого не
импортируется ни библиотекой, ни сервисом (`gar_functions.py` лежит в
`document_processing/ctc/`, но нигде не вызывается), так что оставить его в ветке
безвредно.

## Проверка перед мержем

```bash
python -m pytest tests/                                    # ожидается: 184 passed, 5 skipped
RUN_QUALITY=1 python -m pytest tests/test_quality.py -v    # ожидается: 4 passed (~70 с)
```

Оба прогонялись на Windows после каждой правки. **Прогоните ещё и на Linux, если
есть где** — вся причина существования правок №1-2 в том, что Windows их не
показывает.

Сервис вручную:

```bash
docker build -t russiandocs:latest .
docker run -d --name rd-cpu -p 8003:8002 -e COMPUTE_DEVICE=cpu \
  -e JWT_SECRET=x -e DEFAULT_API_KEY=k russiandocs:latest

```

На GPU-хосте то же с `--gpus all` — ожидается `device=gpu ocr_device=cpu`
(разные устройства для детекторов и OCR — так задумано, см.
[`service/README.md`](../service/README.md)).

## На что посмотреть внимательно при ревью

Не потому что там ошибка, а потому что это места, где ошибку легко пропустить:

- **`service/ml/runtime.py`** — ядро проекта. Его докстринг перечисляет 10 правил
  корректности со ссылками на строки библиотеки. Если ревьюить один файл — этот.
- **Дисциплина лизы.** `process_img` не вызывается нигде вне `lease_pipeline()`, и
  преобразование результата происходит **внутри** лизы. Нарушение любого из двух
  даёт гонку, которая не воспроизводится при ручной проверке в одиночку и
  проявляется как поля от чужого документа.
- **`--workers 1`.** Индекс хранилища и пайплайн — на процесс. `main.py` падает с
  `CRITICAL` при другом значении; не «исправляйте» это как перестраховку.
- **`.dockerignore` написан как allowlist.** Так сделано намеренно: у соседних
  сервисов он начинается с `*.json`, и скопированный оттуда вариант молча выкинул
  бы `models/*/ONNX/model.json`. Сборка дополнительно проверяет число моделей.
- **Секреты в образ не запекаются.** `JWT_SECRET` и `DEFAULT_API_KEY` — только
  переменные окружения; захардкоженного дефолтного ключа нет намеренно (иначе все
  забывшие настроить деплои делили бы один публично известный ключ).
- **Персональные данные.** В `samples/` и `service/seed_data/` только обезличенные
  документы из репозитория. Прогревочное изображение и сид-данные обязаны
  оставаться такими: прогрев читает файл при каждом старте. Проверьте, что в
  диффе нет ничьих настоящих документов — при разработке использовался локальный
  файл вне репозитория, и он в него не попадал.

## Что осталось незакрытым (не блокирует мерж)

1. **SQL-бэкенд намеренно оставлен как справочная реализация, а не как
   законченная функция** — решение заказчика: «SQL пока за скобками, пусть его
   юзеры сами реализуют по рекомендациям». Что есть: протокол хранилища
   (`core/store.py`) с двумя реализациями, модели и миграция Alembic
   (`core/db_sql.py`, `migrations/`), и 45 тестов, параметризованных по
   `[files, sql]` — этот набор доказывает отсутствие диалектных допущений *в
   сервисе* и служит спецификацией. Чего нет: прогонов на живом MS SQL и
   PostgreSQL. **По умолчанию база не используется вовсе**, так что это не влияет
   на работу сервиса «из коробки». Не считайте это недоделкой к исправлению перед
   релизом.
2. **`msodbcsql18` не ставится в образ** (≈100 МБ и EULA в каждой сборке). Для
   MS SQL его нужно добавить в стадию 2 `Dockerfile` — см. п. 1, это работа
   пользователя, а не релиза.
3. **Тайминги в `service/seed_data/` — иллюстрация, не бенчмарк.** На машине
   разработки они шумят в разы: один прогон дал 3219 мс на `DL_2020`, следующий —
   506 мс на том же файле.
4. **`AddressLines`/`INTPASSPORTADDR` не покрыт эмпирически** — в `samples/` нет
   ни одного такого документа, поэтому типы `obbox` и `p_handwritten` в
   `transform.py` подтверждены только чтением кода. Для golden-файлов адресной
   ветки нужен обезличенный сэмпл.
5. **Порт на Go** — отдельная задача. Ветка к нему подготовлена (узкая граница
   `service/ml/`, контракт с округлением float на сервере, `fields` массивом,
   даты ISO-8601 UTC), но сам порт вне рамок.
