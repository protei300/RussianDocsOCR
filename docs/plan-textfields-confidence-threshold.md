# План: умное снижение порога детекции текстовых полей (TextFields)

Адресовано коллеге, который будет это реализовывать. Это план/направление для обсуждения,
**не готовое ТЗ** — перед началом работы стоит свериться по разделу «Открытые вопросы» ниже.

Пороги в коде **пока не трогали** — только диагностика и дизайн.

## Проблема

`TextFieldsDetector` (`document_processing/models/TextFields/ONNX/model.json`) использует
единый глобальный порог `CLS = 0.7`, применяемый **до** NMS ко всем классам сразу
(`YOLODetectorPostprocessing.__call__`, `document_processing/processing/postprocessing.py:294`):

```python
vector = vector[vector[..., 4:4+n_classes].max(axis=1) > self.cls]
```

Реальный найденный кейс (на приватном тестовом документе): поле `Licence_number` чётко видно
на фото, сеть его детектирует корректно с confidence **0.518**, но порог 0.7 отсекает —
`Licence_number` в результате пайплайна отсутствует полностью. Снижение порога до ~0.4-0.5
возвращает поле. Но наивное глобальное снижение порога рискует пропускать «мусорные»
низкоуверенные детекции там, где поля реально нет в кадре (обрезано, закрыто пальцем/голограммой,
отсутствует для данного под-типа документа).

## Идея (черновая, из обсуждения)

Разделить логику на «recall» и «отбор»:
1. Снизить порог **до NMS**, чтобы не терять пограничные, но верные детекции (кейс 0.518).
2. **После** NMS, для каждого класса (имени поля) отдельно:
   - 0 боксов → поле отсутствует (как сейчас).
   - 1 бокс → взять его.
   - >1 бокса того же класса (NMS их не объединил — они физически не перекрываются, напр.
     номер напечатан дважды на развороте внутреннего паспорта) → взять только с максимальным
     confidence, остальные выбросить.

Это обобщение уже существующей логики: `Pipeline._duplicate_field_indices`
(`document_processing/pipeline/pipeline.py`) **уже делает именно это** — но только для двух
захардкоженных полей (`Licence_number`, `Issue_organisation_code`). Судя по тестам
(`tests/test_field_dedup.py`), функция уже параметризована списком полей — расширение на
**все** поля должно быть минимальным изменением (передать полный список field-имён вместо
двух).

## ⚠️ Важное техническое ограничение — до реализации прочитать

Дизайн прогнали через отдельное ревью (модель Opus, только чтение кода). Два momента, которые
меняют картину:

### 1. Правило «1 бокс → всегда брать» — самое слабое место дизайна

Одиночная низкоуверенная **ложная** детекция — реальный сценарий (поле обрезано кадром,
закрыто, отсутствует для этого под-типа документа). Хуже всего: OCR **никогда не возвращает
«ничего»** — на мусорном кропе он выдаст правдоподобный, но неверный текст, который может даже
пройти структурную валидацию (например, формат даты) и **тихо испортить запись**. Пустое поле —
честная, детектируемая неудача; уверенно выглядящее неверное значение — нет.

**Рекомендация ревьюера:** не делать отдельный «пол ниже recall-порога» — сам recall-порог и
есть граница «взять одиночный бокс». Начинать консервативно (**~0.35–0.45**, не 0.15). Кейс
0.518 отбивается уже при пороге 0.45; порог 0.15 в основном впустит шум. Без размеченных данных
обосновывать порог нужно от **известного истинного** случая (0.518) минус небольшой запас, а не
произвольным понижением.

### 2. NMS в проекте — **class-agnostic** (это не тюнинг, это вопрос корректности)

`self.nms` (`postprocessing.py`, метод `nms`) сортирует по максимальному confidence класса и
подавляет **любой** бокс с IOU > 0.2 **независимо от класса**. Это значит: снижение порога —
не безобидная операция. Новые низкоуверенные боксы **разных** классов теперь попадают в один
общий пул подавления. Два пространственно близких поля (например, `Birth_place_ru` и
`Living_region_ru`, или ru/en-пары одного поля), которые перекрываются на IOU > 0.2, теперь
могут подавлять друг друга там, где раньше оба просто не доходили до порога. Итог зависит от
того, чей confidence оказался чуть выше — **это может СНИЗИТЬ recall для соседних полей**,
то есть эффект, обратный цели.

**Вывод:** нужно либо перейти на **per-class NMS** для TextFields (батчинг с classoffset-трюком
или аналог), либо явно проверить (см. план валидации ниже), что при новом пороге пул IOU=0.2
не создаёт неожиданных подавлений между разными полями. Это не просто «покрутить цифру» — надо
подтвердить эмпирически.

Также отдельно: **`IOU = 0.2`** сам по себе довольно агрессивный порог (обычно 0.45–0.6 в
YOLO-пайплайнах). Вместе с пониженным confidence-порогом стоит пересмотреть и его.

## Где реализовывать

**Предпочтительный вариант — ничего не менять в `postprocessing.py`.** Причина: эта
постобработка (`YOLODetectorPostprocessing`, `"Type": "YOLODetector"`) — общая для **трёх**
детекторов: `TextFields`, `Words` (`document_processing/models/Words/ONNX/model.json`) и
`Borders`/`DocDetector` (`document_processing/models/Borders/ONNX/model.json`). У `Words`
**множество боксов одного класса — это ожидаемое, нужное поведение** (каждое слово в поле —
свой бокс класса «word»); блочный коллапс сломает его полностью. У `Borders`, вероятно, тоже
не единичная семантика (разворот паспорта — два сегмента страницы).

Значит:
1. **Коллапс дублей** (шаг 2 выше) — реализовать целиком в `pipeline.py`, обобщив
   `_duplicate_field_indices` на все поля вместо двух захардкоженных. Это не трогает
   `postprocessing.py` вообще и не затрагивает Words/Borders — минимальный риск.
2. **Порог `CLS`** — понизить только в `TextFields/model.json` (не в Words/Borders).
3. **Если проблема #2 (class-agnostic NMS) подтвердится эмпирически** — это уже вопрос к
   `postprocessing.py`, но НЕ как флаг на существующем общем классе (риск регрессии для
   Words/Borders через параметры со значением по умолчанию). Ревьюер предлагает отдельный
   `"Type"` в JSON-схеме — например `"SingleInstanceYOLODetector"` — с собственной,
   per-class-aware NMS-логикой, используемый только в `TextFields/model.json`. Чище, чем
   плодить флаги на общем классе.

## Что НЕ трогать

- `IOU`/логику NMS для `Words` и `Borders` — их мульти-инстансная семантика корректна как есть.
- Сам факт единого порога `CLS` в `postprocessing.py` как код — если проблема #2 не
  подтвердится, трогать `postprocessing.py` вообще не нужно.

## План валидации (без размеченного датасета bbox-уровня)

В проекте нет ground truth на уровне bounding-box'ов для полей (только текстовые GT-строки в
`samples/*.json` для smoke-тестов). Ревьюер предложил дешёвый способ получить направленный
сигнал без разметки полного датасета:

1. **Размечать только «дельту».** Прогнать текущий пайплайн по `samples/` на нескольких
   кандидатных порогах (например 0.35 / 0.45 / 0.55), выгрузить кропы + confidence **только
   для НОВЫХ детекций**, появившихся по сравнению с текущим порогом 0.7. Вручную просмотреть
   только их (пара десятков документов на тип — работа на несколько часов, не датасет).
2. **OCR-результат как слабая метка.** Если новая детекция при прогоне через OCR не проходит
   существующую структурную проверку (формат даты, поиск кода ФМС по словарю, длина поля) —
   это вероятный ложноположительный сигнал, без разметки.
3. **Регрессионная защита.** Убедиться, что GT-строки существующих pytest smoke-тестов
   (`tests/test_textfields.py`, `tests/test_field_dedup.py`, per-doctype `samples/*/*.json`)
   не изменились — и отдельно проверить, что ни у одного **ранее корректного** поля значение
   не поменялось (это ловит именно проблему #2 — перестановку подавления между классами).

## Файлы, которые скорее всего придётся трогать

  `_split_words` на все поля вместо `('Licence_number', 'Issue_organisation_code')`.

  `IOU`, если решим его тоже пересматривать).

- `tests/test_textfields.py` — добавить regression-кейс с реальным документом, где сейчас

- `document_processing/processing/postprocessing.py` — **только если** подтвердится проблема
  #2 (class-agnostic NMS) и решим делать per-class NMS отдельным JSON `"Type"`.
