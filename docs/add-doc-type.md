# Добавление нового типа документа

Этот файл — процедура для мейнтейнера: **что сделать, чтобы новый тип документа
появился не только в распознавании, но и во всём, что распознавание проверяет и
демонстрирует**. Порядок шагов не косметический: каждый закрывает конкретную
аварию, случившуюся в этом проекте; причины приведены рядом с шагами.

Урок, из которого родился файл (релиз 4.2.0): свидетельства о рождении завели в
классификатор и детектор, **не заведя в тесты**. Три бага с одним корнем:
классификатор определял тип, детектор находил поля, а все три порта молча
отдавали ноль значений — и показывали «44/44 зелёные», потому что для тестов
типа не существовало.

Смежное: [`models-release.md`](models-release.md) — выпуск набора весов (новый
тип почти всегда означает и новый набор), [`CHANGELOG.md`](../CHANGELOG.md) —
запись `[4.2.0]` описывает, как выглядело закрытие этого пробела.

---

## Главное правило: тип существует, только если его видят тесты

Цепочка видимости устроена так:

```
samples/<ТИП_ГОД>/  →  service/core/seed.py::_TYPE_ORDER  →  сид-манифест
                                                          →  conformance-кейсы всех портов
```

Сид-билдер обходит кортеж `_TYPE_ORDER`; conformance выводит список кейсов из
сид-манифеста (`conformance/cases.py`) — **второго рукописного списка нет
намеренно**, чтобы демо-данные сервиса и кейсы не могли разъехаться. Обратная
сторона той же медали: тип, которого нет в кортеже, не имеет ни сид-документа,
ни conformance-кейса — для тестов он невидим, сколько бы моделей его ни знало.
Именно так свидетельства о рождении доехали до продакшена с портами,
не реализовавшими тип вообще.

Поэтому весь смысл процедуры ниже — провести тип через **обе** половины:
распознавание (шаги 1–2) и проверку (шаги 3–6).

## Процедура

### 1. Данные и модели: синтетический конвейер

Полный конвейер «чистый бланк → spec раскладки → генерация → дообучение трёх
сетей (DocTypeAngles, TextFields, Borders) → пороги → замеры-ворота» описан в
плейбуке `skills/add-doc-sample-synthetic/SKILL.md` — это внутренний документ
мейнтейнера (в публичный репозиторий не входит), схема отработана дважды:
BIRTHCERT_1998 и BIRTHCERT_2004, вторым заходом распознано реальное фото,
которого система никогда не видела.

Здесь важны только два правила, которые аукаются за пределами обучения:

- **Имя класса — `<ТИП>_<ГОД_НАЧАЛА_ОБРАЗЦА>`** (`BIRTHCERT_1998`). Разные
  образцы одного документа — разные классы, как эры паспортов. Это имя дальше
  фигурирует везде: папка в `samples/`, кортеж сида, слаг conformance-кейса.
- **Пороги моделей калибруются под новый чекпоинт, а не наследуются** — и веса
  публикуются отдельной процедурой [`models-release.md`](models-release.md)
  со своим тегом `models-<набор>`. Не привязывайте набор весов к версии кода:
  веса v4 однажды оказались опубликованы под тегом релиза, код которого
  о свидетельствах ничего не знал.

### 2. OCR-опции: эталон и все три порта

Классификатор и детектор выучили тип на шаге 1, но **какие поля у типа и каким
движком их читать** — это отдельная таблица, и она продублирована в четырёх
местах. Пропуск любого из них не падает — он молча возвращает пустые опции,
то есть документ «распознаётся» в ноль полей:

| реализация | файл | функция |
|---|---|---|
| эталон (Python) | `document_processing/pipeline/pipeline.py` | `OCROptionsClass.make_options` + класс `OCROptions<ТИП>` |
| Go | `ports/go/internal/docproc/pipeline/ocroptions.go` | `MakeOcrOptions` |
| .NET | `ports/dotnet/src/RussianDocs.DocumentProcessing/Pipeline/OcrOptions.cs` | `OcrOptions.For` |
| Kotlin | `ports/java/docproc/src/main/kotlin/net/russiandocs/docproc/pipeline/OcrOptions.kt` | `forDocType` |

Правила, одинаковые для всех четырёх:

- **Диспатч — цепочка substring-проверок, и её порядок несёт нагрузку:**
  `intpassportaddr` обязан проверяться раньше `intpassport` (первое содержит
  второе; перестановка молча уводит страницу прописки в обычный путь полей).
  Новый тип добавляется **той же веткой в том же месте цепочки во всех
  четырёх файлах**, списки `needed_split`/`en_fields`/`ru_fields` — идентичные.
- **Неизвестный тип возвращает пустые опции, а не ошибку.** Это осознанное
  решение (пайплайн не должен падать на будущих типах), но оно же делает
  пропущенную ветку бесшумной — единственная защита от этого шага 4–6.
- Если у типа особая маршрутизация слов по движкам (как чётностное правило
  SNILS), она живёт отдельно — в `Ocr.cs`/`Ocr.kt`/`ocr.go` — и тоже зеркалится.

Авария-первопричина: в 4.2.0 ветка BIRTHCERT была в эталоне, но не в одном из
диспетчеров портов. Go проверяли на реальном свидетельстве против эталона
(11/11 полей), .NET и Kotlin ловились только conformance-кейсом.

### 3. Обезличенный образец в `samples/`

Правила — в [`samples/README.md`](../samples/README.md), они жёсткие, потому что
файлы отсюда попадают в тесты, голдены conformance, сид-данные сервиса и прогрев
моделей — то есть в публичный репозиторий:

- **ни одного документа реального человека** — только синтетика (как
  `2_SYN_BIRTHCERT_2010`) или обезличенный образец: изменённые данные, размытое
  лицо с надписью «образец»;
- папка `samples/<ТИП_ГОД>/`, пара `<stem>.jpg` + `<stem>.json` с одинаковым
  stem;
- GT-json — плоский объект «метка класса TextFields → значение, как изображено»
  (заглавными; не «как в каком-то исходном документе»).

Для типа, добавляемого через синтетику, образец бесплатен: это один из
сгенерированных документов. Проверьте, что его читает эталонный пайплайн, —
он станет лицом типа во всех голденах.

### 4. Сид сервиса: `_TYPE_ORDER`

Добавьте тип в кортеж `service/core/seed.py::_TYPE_ORDER` **тем же коммитом,
что и образец**, и пересоберите сид:

```bash
python service/tools/build_seed_data.py
```

Билдер возьмёт первый по алфавиту `*.jpg` из `samples/<ТИП>/`, прогонит через
эталонный пайплайн и положит `result.json` + канвас + превью в
`service/seed_data/`. Эти файлы — одновременно демо-данные сервиса и golden'ы:
порт сервиса на другой язык обязан воспроизводить их байт-в-байт.

Причина существования шага — та самая авария из преамбулы: комментарий над
кортежем теперь прямо говорит «THIS TUPLE IS WHAT MAKES A TYPE VISIBLE TO THE
TEST SUITE». Тип вне кортежа не существует для тестов.

### 5. Conformance-кейс и голдены

Кейс появляется **автоматически** после шага 4 — список выводится из
сид-манифеста. Остаётся перегенерировать голдены и убедиться, что эталон
сходится сам с собой:

```bash
python -m conformance.refcli regen
python -m conformance.runner run --port python   # обязано быть 0 расхождений
```

Два правила из [`models-release.md`](models-release.md) действуют и здесь:

- **Перегенерация — осознанный акт, отдельным коммитом.** Прежде чем коммитить,
  объясните себе каждое изменившееся число (новый тип не должен трогать голдены
  чужих типов; если тронул — вы меняли не только тип).
- **Голдены — функция от весов**: `regen` пишет имя набора в
  `conformance/cases/models.json`, раннер сверяет его до сравнения чисел.

И правило, купленное первой поставкой BIRTHCERT-голденов:
**проверяйте новые голдены в обеих эталонных средах** — корпоративный venv
(onnxruntime 1.22) и venv публичного чекаута (1.27). Первая поставка упала
ровно на меж-версионной нестабильности OCR: пограничные срабатывания движка на
артефактах пунктирных линеек давали разный мусор в 1.22 и 1.27. Если версии
расходятся — причина почти наверняка в таких пограничных пикселях, и чинить
надо детерминированность значения (как чистка ruler-артефактов в 4.2.0),
а не подгонять голден под одну из сред.

### 6. Прогнать conformance всех портов

```bash
python -m conformance.runner run --port go
python -m conformance.runner run --port dotnet
python -m conformance.runner run --port java
```

Исполняемые файлы портов регистрируются в `conformance/ports.json`; как собрать
каждый порт (и как прогнать Go-порт на машине без Go-тулчейна — через его же
Docker-образ, в котором conformance-CLI лежит рядом с сервисным бинарём) —
в [`ports/README.md`](../ports/README.md). Красный прогон здесь — это и есть
сработавшая защита от аварии шага 2: порт без ветки нового типа теперь падает,
а не зеленеет.

### 7. Обновить документацию и закоммитить

- [`CHANGELOG.md`](../CHANGELOG.md) — запись по образцу `[4.2.0]`: что появилось,
  и почему пробел не ловился раньше;
- `training-datasets.md` и `progress-log.md` — внутренние журналы мейнтейнера
  (датасеты/сплиты ретрейнов и замеры с обоснованиями; в публичный репозиторий
  не входят, но ведутся тем же заходом);
- [`samples/README.md`](../samples/README.md) — если у нового типа есть
  особенности обезличивания.

## Сводный чек-лист

| # | что | где | защита от чего |
|---|---|---|---|
| 1 | модели знают тип | три ретрейна + веса по `models-release.md` | — |
| 2 | OCR-опции | эталон + Go + .NET + Kotlin, одна и та же ветка | «ноль полей молча» |
| 3 | образец | `samples/<ТИП_ГОД>/` + GT-json | утечка ПД; типу нечем стать кейсом |
| 4 | сид | `_TYPE_ORDER` + `build_seed_data.py` | тип невидим тестам |
| 5 | голдены | `refcli regen` отдельным коммитом, две среды | межверсионная нестабильность |
| 6 | порты | `runner run --port go/dotnet/java` | пропущенная ветка теперь красная |
| 7 | доки | CHANGELOG + журналы мейнтейнера | — |

Проверка «всё ли я сделал» одной строкой: `git grep -l <ТИП>` обязан находить
как минимум `pipeline.py`, три `OcrOptions.*`, `seed.py`, папку в `samples/` и
кейс в `conformance/cases/`.
