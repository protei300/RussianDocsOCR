# Выпуск набора весов

Веса моделей **не хранятся в git** (с 2026-08-07). Они лежат ассетами релиза
публичного репозитория, а их состав зафиксирован в
[`document_processing/models.lock.json`](../document_processing/models.lock.json):
путь, размер и SHA-256 каждого из 29 файлов.

Этот файл — процедура для мейнтейнера: **что делать после переобучения любой
модели**. Порядок шагов не косметический, каждый закрывает конкретную аварию,
случившуюся в этом проекте; причины приведены рядом с шагами.

Смежное: `training-datasets.md` (реестр «какая сеть на чём обучена») и
`progress-log.md` (обоснования и замеры) — внутренние журналы мейнтейнера,
они ведутся вместе с выпуском набора, но в публичный репозиторий не входят.

---

## Главное правило: две независимые оси

**Версия библиотеки и набор весов нумеруются отдельно и не связаны.**

| ось | где живёт | пример |
|---|---|---|
| версия библиотеки | `document_processing/__init__.py::__version__`, теги `vX.Y.Z` | `3.0.2` |
| набор весов | `models_version` в манифесте, теги `models-<набор>` | `v4` |

Почему так. Веса меняются своим ритмом: Borders v4 приехал 4 августа, через три
дня после релиза `v3.0.2`, и без поднятия версии библиотеки. Когда номер набора
брали из `__version__`, веса v4 оказались опубликованы ассетами релиза `v3.0.2` —
то есть под тегом, код которого о свидетельствах о рождении ничего не знал.
Разделение убирает и это, и обратную проблему: переобучение больше не требует
релиза кода, а релиз кода — перезаливки 225 МБ.

## Процедура

### 1. Положить новые артефакты на место

`document_processing/models/<Модель>/ONNX/` — `model.onnx` и, если менялись,
`model.json`.

> **Пороги калибруются под чекпоинт, а не наследуются.** `model.json` содержит
> `MaskFilter`, `CLS`, `IOU`, откалиброванные под **предыдущие** веса. Дважды
> подряд их перенесли как есть, и оба раза это стоило качества: `MaskFilter=0.9`,
> унаследованный при деплое Borders #19, срезал серию и номер паспорта у края
> ([issue #10](https://github.com/protei300/RussianDocsOCR/issues/10)), а при
> деплое v4 его вернули на 0.9 через три дня после разбора.
>
> Как калибровать — на примере `MaskFilter`: сравнить покрытие человеческой
> разметки на реальных Tier_3 при разных значениях и взять то, где отношение
> к GT около единицы. Для v4: 0.942 при 0.9 против 0.991 при 0.5 → 0.5.
> Отдельно проверить, что снижение не вернуло галлюцинации фона
> (внутренний скрипт оценки на синтетических сценах).

### 2. Пересобрать манифест

```bash
python scripts/build_models_manifest.py --models-version v5
```

Состав берётся **из самого манифеста**, а не обходом каталога: рядом с
задеплоенными весами лежат локальные варианты для A/B (`ONNX_old`,
`ONNX_legacy_backup`, свипы порогов), которые не должны попасть в публикацию.
Новую модель добавляют явно — `--add <путь>`; лишние `model.json` на диске
скрипт называет, но не включает.

Вывод показывает диф к предыдущему набору — «добавлено / изменено / удалено».
Убедитесь, что изменилось ровно то, что вы меняли.

### 3. Разложить ассеты и залить

```bash
python scripts/stage_release_assets.py
gh release create models-v5 dist/models-v5/* \
    --repo protei300/RussianDocsOCR --title "models v5"
```

Ассеты релиза — плоское пространство имён, поэтому `Borders/ONNX/model.onnx`
публикуется как `Borders__ONNX__model.onnx`. Имена берутся **из манифеста**,
которым потом качает загрузчик, — переименовывать 29 файлов руками означает
ошибиться в одном и получить 404 через полгода.

> **Никогда не перезаливайте ассеты уже опубликованного набора.** Скачавший
> вчера и скачавший сегодня получат разные веса под одним именем — ровно та
> невоспроизводимость, ради борьбы с которой манифест и заведён. Изменились
> веса — новый `models_version` и новый тег.

Заливка 225 МБ может оборваться на крупных файлах (у нас — из-за локального
прокси). Дозалить недостающее: `gh release upload models-v5 <файлы> --clobber`.

### 4. Проверить чистую загрузку

```bash
python scripts/fetch_models.py --check
```

А лучше — по-настоящему, на свежем клоне: удалить пару файлов, вызвать
`fetch_models.py` и убедиться, что они приезжают и сходятся по суммам.

### 5. Перегенерировать голдены conformance

```bash
python -m conformance.refcli regen
python -m conformance.runner run --port python   # обязано быть 0 расхождений
```

Голдены — функция от весов: каждый бокс, размер канваса и распознанная строка
получены конкретным набором. `regen` записывает `conformance/cases/models.json`
с именем набора, а раннер сверяет его с манифестом **до** сравнения чисел и при
расхождении отказывается работать с внятным сообщением. Без этой привязки смена
весов выглядела как регрессия: расхождение в 4 пикселя и 247 px Хаусдорфа, из
которых причину не прочитать.

**Перегенерация — осознанный акт, отдельным коммитом.** Прежде чем коммитить,
объясните себе каждое изменившееся число. В последний раз их было три источника
сразу: Borders v4 (геометрия), `MaskFilter` (геометрия) и DocTypeAngles v3
(уверенность типа — она считается как `1 − dist/thresh`, поэтому смена порогов
двигает её даже при неизменной метке).

### 6. Обновить документацию и закоммитить

- внутренние журналы мейнтейнера (`training-datasets.md` — датасет, сплиты,
  скрипт, дата; `progress-log.md` — замеры и обоснование выбора порогов);
- манифест и голдены — в git; сами веса туда не попадут, `.gitignore` закрывает
  `document_processing/models/`.

CI на пуше сам скачает набор по манифесту и проверит суммы.

## Как это устроено

**`scripts/fetch_models.py`** — только стандартная библиотека, потому что
запускается до `pip install` и внутри докер-стадии, где нет ни `boto3`, ни
`requests`. Качает лишь несовпадающее (релиз, тронувший один `model.json`, стоит
килобайт, а не 225 МБ), проверяет SHA-256 и переносит файл атомарно —
недокачанный вес не должен превращаться в загадочную ошибку распознавания.

**Переменные окружения:**

| переменная | зачем |
|---|---|
| `RDOCS_MODELS_ROOT` | каталог, **содержащий** `document_processing/models`. Та же переменная, по которой веса находят порты на Go, .NET и Kotlin |
| `RDOCS_MODELS_URL` | подменить базовый URL. Это и есть путь для закрытого контура: зеркалируете ассеты внутрь периметра, указываете сюда — код не меняется |

**Докер:** `ports/base/Dockerfile.models` качает веса на этапе сборки, и в этот
слой входят только манифест с загрузчиком — правки в остальном репозитории его
не инвалидируют. Для закрытого контура:
`--build-arg RDOCS_MODELS_URL=https://зеркало.внутри/rdocs/models/`.

**Предохранители.** `tests/test_models_manifest.py` роняет сборку, как только
файлы на диске разошлись с манифестом (сети не требует, только хеши). Он же
ловит забытый шаг 2: поменяли `model.json`, не пересобрали манифест — красный
тест на первом же прогоне.

## Смена хранилища

Загрузчик ходит обычным HTTPS по `base_url` из манифеста, поэтому переезд —
одна строка:

```bash
python scripts/build_models_manifest.py --models-version v5 \
    --base-url https://s3.внутри/rdocs/models/v5/ --no-flatten
```

`--no-flatten` сохраняет структуру каталогов в именах объектов: в объектном
хранилище путь и есть ключ, плоские имена нужны только Releases.

Почему сейчас Releases, а не S3: для публичного репозитория трафик бесплатен и
неограничен, версионирование получается само собой, нет ни бакета, ни ключей в
CI, ни счёта. S3 понадобится, если появятся веса **не** под MIT, которые нельзя
класть в публичный доступ, — тогда у корпоративной сборки будет свой манифест и
свой приватный бакет.
