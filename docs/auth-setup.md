# Настройка входа: PIN или учётные записи

Практическая инструкция: как включить нужный режим, где лежат настройки и что делать,
если что-то не так. Почему всё устроено именно так — в [`docs/auth.md`](auth.md).

> **Это демонстрационная авторизация.** Учётные записи хранятся во временном файле и
> **пропадают при каждом перезапуске** вместе с документами. Для постоянного хранения
> пользователей нужна своя база данных — что именно реализовать, описано в
> [`docs/auth.md`](auth.md#что-нужно-реализовать-самим).

---

## Два режима

| Режим | Вход | Кто что может |
|---|---|---|
| **`pin`** — по умолчанию | один общий PIN, по умолчанию `1234` | вошедший может всё; пользователей и ролей нет |
| **`users`** | логин и пароль | роли `viewer` / `operator` / `admin`, управление пользователями, журнал действий |

Режим **задаётся только в конфигурации** и не меняется из интерфейса. Это сделано
намеренно: переключатель в интерфейсе позволил бы одним щелчком вернуть сервис с
паспортными данными к общему PIN или запереть себя снаружи.

**Если не задать ничего, сервис работает как раньше — по PIN.** Существующие
установки после обновления ведут себя точно так же.

## Где лежат настройки

Настройки — это переменные окружения. Задать их можно тремя способами; если одна и та
же переменная задана в нескольких местах, **побеждает переменная окружения**, затем
файл `.env`, затем значение по умолчанию.

### Локально — файл `.env`

Создайте файл `.env` **в той папке, из которой запускаете сервис** (обычно корень
репозитория):

```ini
# .env — не добавляйте в git, он уже в .gitignore
AUTH_MODE=users
```

и запустите как обычно:

```bash
python -m uvicorn service.main:app --port 8002 --workers 1
```

### В Docker — `--env-file`

Файл `.env` **в образ не попадает**, и это правильно: в нём пароли, а образ передают
другим людям. `.dockerignore` пропускает внутрь только нужные каталоги. Поэтому в
контейнер настройки передаются при запуске:

```bash
docker run -d -p 8002:8002 --env-file .env russiandocs:latest
```

или по одной:

```bash
docker run -d -p 8002:8002 -e AUTH_MODE=users russiandocs:latest
```

### Одной переменной в командной строке

```bash
AUTH_MODE=users python -m uvicorn service.main:app --port 8002 --workers 1
```

### Сервисы на Go, .NET и Kotlin

Настройки у всех четырёх реализаций **одни и те же** — те же переменные, те же режимы, та же
страница входа. Отличается только команда запуска (по умолчанию порты слушают 8003, 8004 и
8005):

```bash
AUTH_MODE=users ports/go/bin/rdocs-service --addr 127.0.0.1:8003
AUTH_MODE=users ports/dotnet/src/RussianDocs.Service/bin/Release/net8.0/rdocs-service --addr 127.0.0.1:8004
AUTH_MODE=users java -jar ports/java/service/build/dist/rdocs-service.jar --addr 127.0.0.1:8005
```

На Windows в PowerShell переменная задаётся отдельно: `$env:AUTH_MODE = "users"`, затем
команда. Что ещё нужно каждому порту для запуска (библиотеки ONNX Runtime и OpenCV), — в его
`README.md`.

## Все настройки входа

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `AUTH_MODE` | `pin` | `pin` или `users`. Любое другое значение — это PIN, с предупреждением в логе |
| `AUTH_PIN` | `1234` | PIN для режима `pin` |
| `ADMIN_USERNAME` | `admin` | логин первого администратора в режиме `users` |
| `ADMIN_PASSWORD` | `1234` | его начальный пароль |
| `JWT_SECRET` | *не задан* | секрет подписи сессий, см. ниже |
| `JWT_EXPIRE_MINUTES` | `480` | срок жизни сессии, 8 часов |
| `LOGIN_MAX_ATTEMPTS` | `10` | сколько неудачных попыток входа до блокировки |
| `LOGIN_LOCKOUT_SECONDS` | `300` | на сколько блокируется вход после них |
| `DEFAULT_API_KEY` | *генерируется* | ключ для машинных вызовов API, в обоих режимах |

**`ADMIN_USERNAME` — только латиница, цифры, точка, подчёркивание и дефис**, первым
символом — буква или цифра. Кириллица в логине запрещена: `admin` и `аdmin` с русской
«а» выглядят одинаково, а это разные учётки. Если задать недопустимое имя, администратор
не будет создан, а в лог уйдёт ошибка. Отображаемое имя пользователя может быть любым.

**`JWT_SECRET`.** Если он не задан — или оставлен значением из примеров, — сервис
генерирует случайный секрет при каждом запуске. Тогда после перезапуска все сессии в
браузерах заканчиваются. Для демонстрационного сервиса это нормально: при перезапуске
всё равно исчезают все учётки. Если сессии должны переживать перезапуск, задайте длинное
случайное значение:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

## Типовые сценарии

### Включить учётные записи

1. `AUTH_MODE=users` в `.env` (или `-e AUTH_MODE=users` для Docker).
2. Перезапустите сервис.
3. На странице входа появится форма «логин + пароль» и блок **Demonstration
   credentials** с `admin` / `1234`.
4. Войдите — сервис **сразу потребует сменить пароль**. До смены учётка не может
   ничего, даже посмотреть список документов.
5. После смены вход выполняется заново, уже с новым паролем, а в меню **System**
   появляется пункт **Users**.

### Задать свой пароль администратора

```ini
AUTH_MODE=users
ADMIN_PASSWORD=Длинный-Пароль-42
```

Такой пароль **не печатается** ни на странице входа, ни в логе — показывается только
демонстрационный `1234`. Смену при первом входе сервис всё равно потребует.

### Вернуться к PIN

Уберите `AUTH_MODE` или поставьте `AUTH_MODE=pin` и перезапустите. Учётки перестанут
существовать: пункта Users нет, `/api/v1/users` отвечает 404. Сессии, выданные в режиме
учёток, в режиме PIN **не принимаются** — иначе любой зритель после переключения
получил бы права администратора.

### Проверить, какой режим сейчас работает

```bash
curl -s http://127.0.0.1:8002/api/v1/auth/config
```

`"mode": "users"` или `"mode": "pin"`. Если режим не тот, что вы задавали, поле
`downgrade_reason` объяснит причину. Это же сообщение пишется в лог при старте.

## Роли

| Роль | Документы | Состояние | Пользователи, API-ключи, настройки, логи |
|---|---|---|---|
| `viewer` | только просмотр | просмотр | — |
| `operator` | + загрузка, переобработка, удаление | просмотр | — |
| `admin` | всё, включая удаление всех документов | просмотр | управление |

Роли проверяет **сервер** на каждом запросе. Интерфейс лишь прячет кнопки, которые роли
недоступны, — чтобы не показывать действие, которое закончится ошибкой.

**Последнего активного администратора нельзя понизить, отключить или удалить**, а свою
учётку — удалить. Так сервис не останется без единого человека, способного управлять им.

## Что происходит при перезапуске

Во временном режиме (по умолчанию) при каждом старте:

1. Каталог данных `DATA_DIR` удаляется целиком — документы, учётки, журнал, ключи.
2. Заново создаётся `admin` с паролем из `ADMIN_PASSWORD` и требованием сменить его.
3. Если `JWT_SECRET` не задан, генерируется новый секрет — старые сессии недействительны.

Если в логе при старте появилась строка **`wipe INCOMPLETE`** — очистка не удалась
целиком: какой-то файл держит другой процесс (антивирус, второй экземпляр сервиса,
открытый редактор). Закройте его и перезапустите, иначе останутся данные прошлого
запуска, а администратор сохранит последний пароль.

## Если что-то не так

**Выбрал `users`, а на странице по-прежнему PIN.**
Посмотрите `downgrade_reason` в `/api/v1/auth/config` или в логе. Возможные причины:
опечатка в значении; не установлен `argon2-cffi` (`pip install -r requirements-service.txt`);
задана строка подключения к базе данных — режим учёток работает только с временным
файловым хранилищем. Если причины нет, обновите страницу с очисткой кеша
(`Ctrl+Shift+R`).

**`admin` / `1234` не подходит.**
Пароль уже сменили. Перезапуск вернёт исходный — если в логе нет `wipe INCOMPLETE`.

**«Too many attempts. Try again in N s».**
Сработала защита от перебора. Подождите указанное время или перезапустите сервис.
Блокировка ведётся и по учётке, и по адресу: смена логина её не обходит.

**Браузер подставляет пароль, но не логин.**
Это старая запись в менеджере паролей, сохранённая без логина. Удалите её в браузере
(*Chrome → Настройки → Автозаполнение → Менеджер паролей*, найдите адрес сервиса) —
новые записи сохраняются правильно.

**После перезапуска выбрасывает на страницу входа.**
Так и задумано, если не задан `JWT_SECRET`: секрет новый, прежние сессии
недействительны. Задайте `JWT_SECRET`, если это мешает.

**За обратным прокси (nginx и т. п.) блокировка срабатывает для всех сразу.**
Сервис видит адрес прокси, а не клиента, и все делят один счётчик. Настройте
ограничение частоты на самом прокси или запустите uvicorn с `--proxy-headers
--forwarded-allow-ips=<адрес прокси>`.

## Перед тем как показывать кому-то снаружи

Это демонстрация, но если к ней есть доступ из сети:

- задайте свой `ADMIN_PASSWORD` и длинный случайный `JWT_SECRET`;
- смените `AUTH_PIN`, если остаётесь на PIN;
- ставьте перед сервисом TLS — сам сервис говорит только по HTTP;
- помните, что `/api/docs` (описание API) открыт без входа.

Полный список — в [`SECURITY.md`](../SECURITY.md).
